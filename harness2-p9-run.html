Project 9 run, step by step

Two live runs of project9/ through the released harness2 code (commit 1cfe254), shown as two animations. Each step names the harness2 function that ran, the paper stage, the harness files it touched, and the values it produced.

Two runs, two animations. Both runs did task ledger-1 with budget k = 1, sequential mode and harness2 commit 1cfe254, in WSL. They are different in the number of tasks and in the result.

  • Animation 1, run t1: 1 task. base1 and c1 both wrote the correct total and scored 1, so the result is a tie. Level 2 stops at the library, because no task comes after ledger-1.
  • Animation 2, run live: 3 tasks, and the animation shows task ledger-1. base1 wrote a wrong total and scored 0. c1 wrote the correct total and scored 1. Step 17 shows the next task, ledger-2, as it reads the library.

The two recursions

Each animation has two frames. Each frame is one recursion of the paper, and each has its own loop, drawn as a dashed arrow.

  • Level 1, the teal frame: inside one task. It starts from the base harness H₀ and runs it once (base1). Two editors propose changes (inv1, dom1), each change runs once as a probe, and a composer merges them into c1. That is one round. With a budget of k, sequential mode runs k rounds, and round t + 1 starts from the harness ct of round t (the dashed loop at the top). Both runs had k = 1, so each made one round and did not take the loop.
  • Level 2, the orange frame: across tasks. After the task, the reflector reads the whole record and writes one lesson. The library stores the lesson and the chosen harness. The next task in the domain does not start from c1: it starts again from H₀ (schedule.py:617). Its editors get a copy of the library and can reuse what worked (the dashed loop at the bottom, step 17).

The frame of the active level lights up in each step, and the step card names the level.

How to read the values

Each box shows the stage, the label that harness2 gives it, the model, and the values of that stage. The values in a box appear when the animation reaches its step. Example, from the Composed run box of animation 2: Total: 85.15, $0.047 · 21.6 s.

  • Total: 85.15: the line that the run wrote to answer.txt. The task asks for the signed sum of the ledger: 100.25 − 20.10 + 5.00 = 85.15. Green means that the line is correct. Orange means that it is wrong: Total: 105.25 is 100.25 + 5.00, because the H₀ script drops the negative amount.
  • $0.047: the cost of that one call at API prices, as Claude Code reports it. For a task run it is total_cost_usd in the last line of stream.jsonl. For a session it is cost_usd in audit/*.meta.json. The Claude subscription paid for the runs, so these numbers are estimates, not charges. Animation 1 shows 4 decimal places, because its task runs cost less than $0.01 each.
  • 21.6 s: how long the call took. For a task run it is duration_ms in stream.jsonl (21,625 ms). For a session it is wall_s in audit/*.meta.json.
  • "ran the c1 script": the run called python3 scripts/summarize.py ledger.csv with the script of its own harness. Its log shows that call.
  • "AGENTS.md: 7 → 8" (animation 1): the line count of the file before and after the edit.
  • "byte-equal to inv1" (animation 2): the two editors wrote the same scripts/summarize.py, byte for byte, without seeing each other's work.
  • "R = 4 runs, P = 3": the run count that harness2 records. R is the number of task runs (base1, inv1, dom1, c1). P is the number of editor sessions (inv1, dom1, c1). The reflector session is counted separately.
  • "1 script, 299 chars": the size of the stored harness, from the library index. It has 1 script, and its AGENTS.md has 299 characters. Claude Code loads that file as CLAUDE.md in every run, so it is "always-on" text. In animation 1 the number is 1,059, because the composer rewrote AGENTS.md.
  • "$1.21 for ledger-1" (animation 2): $0.137 for the 4 task runs plus $1.071 for the 4 sessions (3 editor sessions and the reflector). In animation 1 the box shows $0.46: $0.016 for the 4 task runs plus $0.448 for the 4 sessions.
  • The small grey line at the bottom of each box (for example recursion.py:559): the place in the harness2 code where the stage runs.

What the record does not show


    

  • Tool calls inside the sessions. The editor, composer and reflector sessions run with --output-format json. The record keeps each session's mission (*.mission.md), reply (*.response.md), duration and cost, but not the tool calls inside it. The 4 task runs use stream-json, so their tool calls are complete.
    • 

  • Exact start times. In run t1, the record has end times (file write times) and durations, not start times. The run start, ≈ 08:15:34, is the end time minus the 2 min 37 s total, which includes the uv start-up.
    • 

  • Level 2 in run t1. With one task, the library is written but no editor reads it. Step 17 shows the read from the earlier 3-task run in project9/runs/live/.
    • 

  • The Windows shims. Both runs were in WSL, so the two Windows shims in adapter.py (fcntl stand-in at line 22, read_tree replacement at line 36) did not run. On native Windows, the read_tree replacement runs in steps 3 and 7, and the fcntl stand-in runs in step 15.
    • 

  • Run t1: a tie, not a gain. The base run and the final both scored 1. In base1, Haiku did not obey the harness and calculated the total itself. In run live (animation 2), base1 wrote Total: 105.25 and scored 0. One run per arm cannot show that the edits made the harness better; the reflector also rated its own confidence "low".
    • 

  • Run live: a gain on ledger-1 only, from one run per arm. On ledger-2 and ledger-3, base1 and c1 both scored 1, and base1 edited the script during the run. A control run with the library off gave the same 6 scores. project9/evidence/README.md lists these limits.
    •
