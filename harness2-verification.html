Harness² Verification

Round 1, 24 Oct 2026. The Theory tab and the Project 9 section of this site, checked against the Harness² paper and the released code. Each claim on this page gives its source, so you can check it yourself.

Round 1 in brief. I compared the Theory tab (chapters T1 to T6), in 33 rows (19 rows for its 20 numbered definitions and propositions, 14 rows for further claims in its text), with the released code, and with the Project 9 section that builds on that code. 15 rows hold as written, 15 hold only under a condition, 1 differs from the code, and 2 have no code object. The largest correction: the run budget "4k runs per task" is per recursion mode, and the code's default runs two modes, which gives 7k runs per task. The selector of the released code never sees a base run, although the paper's printed selector prompt says that a base run is a valid pick. I changed 8 places on the Theory tab (T0, T1.4, T1.6, T1.7, T1.8, T2, T2.2, T7) and 9 places on the Project 9 page, and added a section of six mapping tables. Reading the paper for this page showed 4 open items for round 2.

1. What was checked

This site has two pages that describe Harness². The Theory tab describes the method as a formal model: definitions and propositions numbered T1.1 to T6.1. The Project 9 section explains how to use the released Python package as an engine. Both pages were written from the paper and the code by the same author (an AI agent), so the two pages can share an error.

The user set three goals for this check:

  1. Verify the theory against the released code.
  2. Connect Project 9 to the theory, item by item.
  3. Fix both pages where they disagree with the code, in rounds. A round maps the items, lists the discrepancies, fixes the pages and reports. A maximum of 3 rounds; stop early when a round finds nothing.

Scope of round 1: every formal item of T1 to T6 (Def T1.1–T1.4, T1.6; Prop T1.5, T1.7, T1.8; Def T2.1, Prop T2.2; Prop T3.1–T3.3; Def T4.1, Prop T4.2; Def T5.1, Prop T5.2–T5.4; Prop T6.1), plus the notes in the text that make claims about the code. Chapters T7 to T9 state no new formal item. On the Project 9 side: every code fact in the section "Project 9 in depth", including the figure captions.

3. How it was checked

3.1 Which source decides

The four sources do not have equal weight. Each kind of claim has one source that decides it. The tag on each Theory item (Paper, Code, Literature or Model) tells which kind of claim it is.

Kind of claimDeciding sourceExample
What the released package doesThe code at 1cfe254, and its tests"Library.add stores nothing without a lesson"
What the paper saysThe paper PDF"each rollout is capped at 200 model turns"
A logical resultThe proof on the Theory tab. The code only tells whether the assumptions of the proof are true.Prop T1.8, label invariance
A design choice of Project 9Nothing outside the pages. Project 9 must agree with itself and must say where it differs from the code.The minimal build lets the selector pick a base run

When the paper and the code disagree, this check does not pick one. It reports both and marks the item.

3.2 Three pair checks, in order

  1. Theory ↔ code. For each formal item, find the code object and its file:line. Give a verdict.
  2. Project 9 ↔ code. Check each code fact of the Project 9 section: the file, the line and the behaviour.
  3. Theory ↔ Project 9. Steps 1 and 2 connect both pages to the same code, so each item joins the two results. Step 3 finds only what is left.

Then, for this page, a fourth pass: paper ↔ the three others, for every item that round 1 touched.

3.3 The triangle: how to read one item

Each item has three cells: the theory (T), Project 9 (P) and the code (C). The pattern of agreement decides the action.

3.4 Verdicts and evidence rules

holds the code does what the item says. holds with condition the item is true only under a stated condition. differs the code does something else. theory only no code object exists.

  • The code was read, not run. The repository tests were read as evidence of intended behaviour.
  • Every code claim has a file:line at commit 1cfe254. A reviewer agent re-checked the line numbers against the printed source; it found one wrong line (534 instead of 535), which was corrected before this page was written.

F1. Def T1.4: a step of Φ draws no new reference run in the code

Paper
§2.2.1, Propose (p. 5): "The pipeline first obtains a reference execution e₀ ∼ A(qt; M, H)." The same paragraph: "Conditioned on the task, current harness, reference, earlier history, and library in Rt, the pipeline proposes two candidates." For sequential recursion, §2.2.2 (p. 6): "The initial history contains k base executions and is extended after each step with ξ(r)." So the paper describes a reference per step in §2.2.1, and k base executions at the start of the sequential chain in §2.2.2. It does not say whether a sequential step draws a new reference.
Code
Every editor and composer stage of both modes receives the base runs: rollouts=base at recursion.py:381, 421, 503 and 550. The docstring of run_sequential says "DEPTH: k nested passes over the same shared base evidence" (recursion.py:466). The base runs are executed once per task (schedule.py:619–626). In round r ≥ 2, the run of the previous checkpoint enters the history (recursion.py:561), and the composer prompt calls it "this round's on-policy evidence" (prompts.py:975–979). Composers of both modes and editors of sequential mode also read earlier candidates and decision notes (424–425, 506–509, 553–554). An invalid proposal is retried once, then the stage returns the current harness (recursion.py:242–251); the paper says the same in App. D.2 (p. 21).

7. Open items for round 2

Writing this page showed four items that round 1 did not cover. They are not fixed yet.

O1. Rollout limits: the paper says 200 turns and 3,600 s; the code sets other values

Paper, App. D.1 (p. 21): "Each rollout is capped at 200 model turns and 3,600 seconds (WorkBuddy-Bench uses its container timeout at twice the benchmark default)." Code: the JobBench adapter defaults to 2,400 s for OpenCode and 3,600 s for Codex (benchmarks/jobbench.py:499, used at 641). I found no 200-turn cap in harness2/ or scripts/; the JobBench OpenCode runner reads AGENT_STEPS, which is empty by default (benchmarks/jb_opencode_runner.py:92). Pattern: Paper ≠ C. The Theory tab cites the paper's values as Paper (correct as a paper claim); #p9-t1 already gives the code's 2,400 s. Proposed action: add one Code sentence to Def T1.2.

O2. T2 cites App. D.2 for "each domain's library starts empty"

App. D.2 (p. 21) says "Each benchmark domain has its own library directory". The words "starts empty" are in §3.1 (p. 7), for "each benchmark stream". Proposed action: cite both places.

O3. Def T1.4 still omits the history from the kernels

The paper conditions Propose on "the task, current harness, reference, earlier history, and library" (§2.2.1, p. 5), and the code passes the history to sequential editors and to all composers (F1). The definition, tagged "Model of Paper Eq. 1", writes πINV(· | q, H, e₀, L) without 𝓔. The round 1 Code paragraph states the difference, but the definition itself is narrower than the paper. Proposed action: add 𝓔 to the arguments of πINV, πDOM and κ.

O4. The Tutorial tab and the README repeat two of the round 1 errors

Round 1 covered the Theory tab and Project 9 only. The Tutorial tab of harness2-learn.html has the same two statements that F3 and F4 corrected: (1) in "Final selection (k > 1)": "Picking an output from the unmodified harness is valid (Prompt 5)", with no note that the released code never offers a base run (F4); (2) in "Count the runs": "In both modes the first k runs are shared base runs, and the totals are the same: 4k runs and 3k counted sessions", which is correct per mode but does not say that running both modes gives 7k (F3). The README says "4k executor runs, 3k improver sessions" with no mode qualifier. Proposed action: add the code's behaviour to both Tutorial paragraphs and "per mode" to the README.
