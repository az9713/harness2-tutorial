Harness² Project Ideas

Ten projects that use the Harness² method (arXiv:2610.14224) on a Claude Code setup. Each one shows which part of the method it reuses, the files to create, the run cost, the evidence from the paper, and the risks. Companion to Learn Harness².

How to read this report

Every project is a part, or all, of the Harness² pipeline: a reference run, two editors that propose edits, probe runs, a composer, a blind selector, and a reflector that writes to a library. Each idea's diagram colours its boxes by the pipeline stage it plays. So you can see at a glance which stages the idea reuses and which stages it leaves out.

Reference / execution run Propose (editor, Prompt 1) Probe (contrast run or check) Compose / decide (Prompt 3) Select (Prompt 5) Reflect / library (Prompt 6) Your files, or a step outside Harness²

Each section has the same parts: what it is, the mapping onto Harness², a diagram, the build (file tree and short snippets), and four facts: cost, evidence, risk, first step. The snippets are sketches to hand to an agent. They are not tested code. Ideas 1 and 4 also have a step-through animation, because the earlier answer recommended them as the starting points. Project 9 has its own walkthrough, Project 9 in depth, with two animations, for readers who are new to Harness².

One fact changes how most of these ideas are built. The released code (google-research/harness2) runs its executor on two substrates only: OpenCode and Codex (harness2/substrate/opencode.py, codex.py). Its claude_cli channel runs the editors through the Claude CLI, not the executor (harness2/core/proposer.py). So ideas 1–8 and 10 re-implement the method inside Claude Code by hand, and only idea 9 uses the released code directly. One detail keeps a Claude Code executor possible in idea 9: the core of the package uses only a substrate's name and its file layout, and the adapter's own execute() runs the task (see where project 9 falls short).

What "recursive" means in Harness²

The paper calls Harness² "recursive agent harnessing". The word has a narrow meaning here, and the meaning decides which of the 10 projects show the method and which only use a part of it. The paper's definition couples two updates: task-level recursion "refines the current execution harness using generated harnesses and execution evidence", and harnessing-level recursion "updates the improvement harness that guides this refinement" (paper §2). In both, an output of the improvement process becomes an input of the next improvement. Fig. R1 shows the two loops, and one shape that is not a loop.

Fig. R1 — Top: level 1 in sequential mode is a chain, where each step starts from the previous step's harness. Middle: parallel mode spends k as width; nothing is fed back, so it is one generation, not a chain. Bottom: level 2 feeds what task t learned to the editors of task t+1, while the harness itself restarts from H₀. Source: paper Eq. 2–4 and §2.2.2.

Level 1: depth within one task

In sequential mode, step r starts from the harness that step r − 1 composed, and it reads every earlier run of the task: H⁽ʳ⁾ = Φ(H⁽ʳ⁻¹⁾, 𝓔⁽ʳ⁻¹⁾) (Eq. 3). The code does this in run_sequential: current_harness = comp.tree at the end of each round (harness2/core/recursion.py). Parallel mode is different. The paper says its implementation "performs one population update; k controls its width rather than its depth" (§2.2.2). Parallel mode makes several candidates and composes from all of them, but no composed harness is edited again. At k = 1 the two modes are the same procedure, and that procedure is one application of Φ: a single step at k = 1 is not a recursion.

Level 2: across tasks

After each task, the reflector writes the adopted harness and a lesson into the library, and the next task's editors read the library (Eq. 4: 𝓡ₜ₊₁ = Update(𝓡ₜ, H★ₜ, 𝓓ₜ)). In the code, the library folder is copied into the context of every editor session (harness2/core/context.py). The execution harness does not carry over: every task starts again from H₀. What carries over is the improver's knowledge. A loop in which the working agent reads its own notes is useful, but it is memory for the executor, not level 2 (see idea 2).

What "recursive" does not mean here

Neither level rewrites the improvement code. The editor, composer, selector and reflector prompts and the editor model stay fixed; the improvement harness "is updated afterward through its harness improvement library" (§2). So the recursion is feedback through data, in the sense of a fold over steps and over tasks (Theory tab, T2). It is not a program that rewrites its own source, as a Gödel machine would.

How to check that a build is recursive

LevelThe evidence to look for in the recordsThe test that measures it
Level 1A composer decision line in step 2 that cites a moment in step 1's checkpoint run, e.g. kept -> <edit> -> <moment in the c1 run>.Compare sequential k = 2 with k = 1 on the same task (paper Fig. 5 does this for k = 1 … 5).
Level 2An editor note on task t+1 that names a library entry from task t that it copied or adapted.Re-run task t+1 with an empty library. The difference is the library's effect (paper Table 3: −3.1 on WorkBuddy-Bench, −1.8 on JobBench without it).

The 10 projects, ranked by recursiveness

The rank uses the two tests above. A project is full if it has both loops, partial if it has one loop only under a stated condition, a loop that is not level 2 if it feeds back to the executor instead of the improver, a single step if it applies Φ once, and a component if it is a part of a step (a probe, a checker, a selector). Two changes turn ideas 2 and 3 into this build:

  1. Chain the steps. Step 2 starts in a fresh worktree copied from wt-final of step 1 (the checkpoint c1), not from HEAD. Its editors and composer receive every earlier run: both base runs, the step-1 probes and the c1 run. This is the code's run_sequential loop.
  2. Move the library to the editors. The reflector writes to library/. No SessionStart hook prints it to the working agent. Instead, the editor prompt tells the editors to read library/INDEX.md, and to treat a copied fact as "a hypothesis here, not a fact" (Prompt 1).
CostPer task at k = 2: 8 runs (2 base, 4 probes, 2 checkpoints), 6 counted sessions, 1 selector, 1 reflector. Two tasks: 16 runs. The empty-library re-run of task 2 adds 8 runs.
Level-1 evidenceA step-2 decision line that cites the c1 run.
Level-2 evidenceA task-2 editor note that names the task-1 entry, and the difference against the empty-library re-run.
LimitOne task pair gives one contrast, with no noise estimate. The paper averages three runs per score; treat a single pair as a demonstration, not a measurement.

Project 9 in depth: the released code as a level-2 engine

This part needs no Harness² background. It explains what the package does, shows where its code does level 2, lists its limits, and ends with a decision guide, a cost calculator and a build plan. The code facts come from google-research/harness2 at commit 1cfe254 (13 Oct 2026). I read the code on 24 Oct 2026 and did not run it.

Project 9 in five sentences. Harness² improves the files around an AI agent (its prompts, skills and scripts), not the model. Google released the method as a Python package, harness2. Project 9 uses that package as the engine: you write one adapter class that tells it how to list, run and read your tasks. The package then runs both levels of the method, and level 2 needs no extra work, because the package keeps one library per group of tasks and gives it to the editing sessions of every later task. The main limits: Linux only, OpenCode or Codex as the shipped agents, 4k agent runs per task, and a library that only grows and stays inside one run setting.

The calculator gives the run and session counts for a planned stream. It uses the package's own rules: k base runs per task are shared by both modes; each mode then adds 3k runs and 3k counted sessions; a selector runs only when k > 1; a reflector runs once per mode after a successful selection.

These are lower bounds. An invalid edit gets one retry (STAGE_ATTEMPTS = 2), and a failed model call one more attempt (TRANSPORT_ATTEMPTS = 2). The hours assume one run at a time; the package runs two at a time inside a phase (PHASE_WIDTH = 2) and can run domains side by side (--workers). A library-off comparison (limit 8) doubles the count for the tasks you compare.

1. Hook compiler from repeated failures

Single step Is it recursive? No. It applies one step Φ to old trajectories, once. It would become a fold if each mining round's editor read the hook entries of earlier rounds; then round n+1 would build on what round n learned.

What it is. A tool that reads your past Claude Code transcripts, finds errors that repeat, and turns each one into a hook that blocks the error every time. A CLAUDE.md rule asks the model not to do something; a hook prevents it. The Theory tab of the tutorial (T4) shows why: a rule such as "never kill a process by name" is a safety property, and a monitor inside the tool loop can enforce a safety property, where a prompt can only lower its probability.

The mapping onto Harness²

Harness² stageIn this project
Reference runsYour transcripts in ~/.claude/projects/*/*.jsonl. They already exist, so this stage costs nothing.
Propose (INV editor, Prompt 1)One editor session per repeated failure signature. Its only allowed outputs are one PreToolUse hook or KEEP_BASE. Prompt 1's rule applies: a defensive hook needs "repeated evidence that clear prose is skipped", and "it must not block valid completion".
ProbeA replay: run the candidate hook on every logged tool call. Count the bad calls it blocks and the good calls it blocks. This is cheaper than the paper's probe, because a hook is a deterministic function of one tool call; no task needs to run again.
ComposeKeep a hook only if it blocks zero good calls in the replay (the transparency condition, Theory T4). Record each decision as kept|dropped -> <hook> -> <replay counts>.
ReflectWrite the hook and an EXPERIENCE.md entry: cue = the failure signature, evidence = the replay counts.

import glob
import json
import os
import subprocess
import sys

hook, blocked = sys.argv[1], []

for path in logs:
    for line in open(path, encoding="utf-8"):

print(len(blocked), "blocked")
print("\n".join(blocked))

2. Reflector hook and experience library

Loop, not L2 Is it recursive? It has a feedback loop, but not the paper's level 2. As designed, the working agent reads the library, so the library improves the execution harness, like the C3 memory component. That is closer to a memory method such as ReasoningBank, which the paper runs as a baseline, than to harnessing-level recursion. The level-2 variant below moves the library to the editors.

What it is. When a session ends, a hook starts a headless reflector session. The reflector reads the transcript and writes at most one lesson to a per-domain library. When the next session starts, a hook prints the library index, not the entries, so the agent can open a relevant entry on demand. This builds only the harnessing-level recursion of the paper (Eq. 4), with no probes.

The level-2 variant. Keep the reflector and the library. Change who reads the library:

  1. Remove the SessionStart hook that prints INDEX.md to the working agent.
  2. Add one line to the editor prompt of idea 3: "Read library/INDEX.md. You may copy a component; treat each copied fact as a hypothesis here, not a fact."
  3. Write library entries only after an improvement step (idea 3), so that each entry rests on a contrast between runs, not on one session.

The memory version is still useful, and it costs less: no probe runs. It is a different mechanism, and the paper's library numbers (Table 3) do not measure it.

3. A /harness-step skill (level 1, k = 1)

Partial Is it recursive? Partly. At k = 1 it is one application of Φ, which is not a recursion. It becomes level-1 recursive when you chain steps: step 2 starts from wt-final of step 1 and reads all earlier runs (sequential k ≥ 2). It reaches level 2 when its decisions go to a library that the next task's editors read. Both changes together are the minimal full build.

What it is. A skill that runs one full Propose–Probe–Compose step on a real task in a git repository. Each harness variant lives in its own git worktree, so the three variants can run side by side without changing each other's files. The deliverable is the output of the composed harness.

4. Always-on diet auditor

Single step Is it recursive? No. It is one step: measure, propose, probe, compose. A repeated audit that reads earlier audit decisions would be a loop, but the auditor gains little from it, because each audit measures the current files from scratch.

What it is. A tool that measures everything that enters the context on every call (CLAUDE.md files, rules, SessionStart hook output, skill descriptions) and proposes a new home for each block in the paper's cost order. The paper's editor prompt states the reason: always-on prose is "competing with the agent's own output budget", and "if you add always-on text, cut something else to pay for it".

        if part.get("type") == "tool_result" and part.get("is_error"):
            errors += 1
print(json.dumps({"turns": turns, "tool_calls": calls, "tool_errors": errors}))
Cost2 arms × tasks × repeats. Example: 10 tasks × 3 repeats = 60 runs, plus 30 for the A-vs-A noise floor.
EvidenceThe paper reports each score as the mean of three runs with shuffled task order (Tables 1–2), because single runs vary.
RiskFixtures go stale when your real tasks change. Too few repeats give a decision inside the noise.
First stepFreeze 10 past inputs of one skill, and run arm A twice to measure the noise floor first.

7. Independent checker library

Component Is it recursive? No. It is a building block for probes. Its value to the recursive projects is the quality of their evidence: a check that the executor did not write keeps a wrong assumption from passing through every step.

What it is. A set of deterministic checker scripts written and reviewed once, outside any task run, and then reused by every other idea. Each checker reports named failures (sheet and cell, file and line) and exits non-zero when it finds one. A skill tells the agent when to run which checker.

The mapping onto Harness²

Harness² pieceIn this project
C7 scriptsThe checkers themselves, e.g. a formula cell that a reader sees as blank, numbers that differ between two files, broken links, missing front-matter fields.
C6 skillOne skill that maps a deliverable type to its checkers.
Probe evidenceChecker output is a behavioural fact that the composer, the A/B bench (idea 6) and the reflector can cite.
Why independentFig. 14: a checker that the editor wrote during the task "reported PASS three times" while the real tests failed (75 → 64). The paper's comment: "A checker written by the editor cannot catch the editor's assumption."

Fig. 7 — Checkers written outside the task give evidence that does not share the executor's assumptions (Theory T3, the checker section).

The build

The paper's Fig. 9 shows the idea of verify_outputs.py: compare a formula with the value a reader sees. This version uses openpyxl, which reads formulas and, separately, the cached values that the last spreadsheet program saved.

# checks/xlsx_blank_formulas.py FILE  formula cells that read blank
import sys
from openpyxl import load_workbook

live = load_workbook(sys.argv[1])                  # formulas as written
seen = load_workbook(sys.argv[1], data_only=True)  # values a reader sees
bad = []
for ws in live.worksheets:
    for row in ws.iter_rows():
        for c in row:
            shown = seen[ws.title][c.coordinate].value
            is_formula = isinstance(c.value, str) and c.value.startswith("=")
            if is_formula and shown in (None, ""):
                bad.append(f"{ws.title}!{c.coordinate}")
print("\n".join(bad))
sys.exit(1 if bad else 0)

A file that openpyxl wrote and no spreadsheet program has recalculated has no cached values, so every formula reports blank. That is the correct warning: a reader who opens the file in a viewer that does not recalculate sees blank cells.

8. Evolve with a strong model, deploy with a cheap one

Full while evolving Is it recursive? Yes, in the evolve phase, if that phase uses ideas 3 and 2 in their recursive forms (chained steps, a library read by the editors). The deploy phase freezes the harness, so the recursion stops there by design: it trades further adaptation for the cheap model's price.

What it is. Run Harness² with a strong executor (for example Opus) on the first N tasks of one kind. Merge the adopted harnesses into one frozen domain harness. Then run that harness with a cheaper model (Sonnet or Haiku), and measure the gain with the A/B bench of idea 6.

The mapping onto Harness²

Consolidate (not in the paper)Merge the library into one harness. The paper lists this as future work (Appendix G). Group components by the job they do (their cue), not by shared lines: the paper found that only 2–10% of modified files keep at least half their lines from a library entry (Fig. 10).
TransferThe cheap model runs the frozen harness. The paper's evidence: the harness evolved for Gemini 3.5 Flash raised GLM-5 on Code from 58.5 to 75.8 (+17.3).

First stepPick a domain with at least 10 similar tasks, and decide what a correct output is before you start.

9. An adapter for the released code

Full, as published Is it recursive? Yes, both levels are implemented. Level 2 runs in both modes and at every k: the library folder is copied into the evidence folder of every editor and composer (harness2/core/context.py:164). The level-1 chain runs only in sequential mode with k ≥ 2: current_harness = comp.tree at the end of each round (harness2/core/recursion.py:562). The CLI default is parallel mode (harness2/cli/_common.py:34). This is the reference against which the other projects are ranked.

What it is. Use the released harness2 package as the engine, with your own task type. You write one adapter class and a short driver script. The package then gives you the full method: parallel and sequential recursion, the ledger, the library, the blind selector and the reports.

Full walkthrough. Project 9 in depth explains this project for a reader who is new to Harness²: ten terms, what you write, two step-through animations (one task, then three tasks), the eight code lines that do level 2, twelve limits, a decision guide with a cost calculator, and a build plan with code sketches.

CostPer task and mode: 4k executor runs and 3k editor and composer sessions, plus 1 reflector, plus 1 selector when k > 1. At k = 1 no selector session runs (trivial_selection). API spend for both the executor and the improver.
EvidenceThe release of the paper's authors. Its tests check the level-2 path on disk (tests/test_workflow.py:108–127). Paper: without the library, −3.1 on WorkBuddy-Bench and −1.8 on JobBench (Table 3).
RiskLinux only (WSL on Windows). The claude_cli channel runs claude --dangerously-skip-permissions -p: run it only in a sandbox (a container or VM with no secrets). The README refers to a .env.example that the repository does not contain.
First stepIn WSL, run harness2-demo --output runs/demo --k 2 and open task 2's context/inv1/library/INDEX.md (build plan, step 2).

10. A domain harness for a pipeline you repeat

Full with k ≥ 2 Is it recursive? Yes, if two conditions hold: improved tasks use sequential k ≥ 2 (level 1), and the library feeds the editors (level 2). The config below sets "k": 2 for this reason; with k = 1 the project has level 2 only.

What it is. Apply both recursion levels to a pipeline that you run again and again, for example source summaries or the build of one textbook module. Each run of the pipeline is one task qt in the paper's stream. The current skill is H₀. A library per domain carries what earlier runs learned.

With improve_every = 3 and k = 2, every third task gets two chained steps (8 runs) and the other two run once: 8 + 1 + 1 = 10 runs per 3 tasks, about 3.3 per task. With k = 1 the cycle costs 4 + 1 + 1 = 6 runs (2 per task), but then only level 2 is recursive. To see whether the library helps, re-run 3 later tasks with an empty library and compare the checker failures; this is the paper's library ablation (Table 3) at small scale.

Cost(4k + m − 1) / m runs per task on average: about 3.3 at k = 2, m = 3; 2 at k = 1, m = 3.
EvidenceThe paper's largest single-task gains came from procedural failures (Fig. 9: 43.1 → 77.8). Removing the library costs 3.1 / 1.8 points (Table 3).
RiskLong tasks make 4 runs expensive. Your review is the grader: if you give it to the editors, they optimise your review, not the task (Theory T3, the grader leak).
First stepWrite down 3 failures the pipeline has had, and one checker for each (idea 7).

Build order

The ideas depend on each other. Ideas 1 and 4 need nothing else. Idea 7 gives ideas 3 and 6 evidence that the executor did not write, and idea 2 supplies the library that ideas 3 and 10 read. Idea 9 is the alternative engine: it replaces your hand-built versions of ideas 3 and 10 with the released code.

Fig. 11 — Build order. An arrow means "makes the next idea work better or is a part of it". Dashed = an alternative path.

Recommended path. To see the recursion itself, add the minimal full build after step (4). (1) Idea 4, to measure where your always-on tokens go. (2) Idea 1, to turn the repeated failures into hooks. (3) Idea 7, one checker for your most common deliverable. (4) Idea 3 on one real task, at 4 runs. Only then decide between ideas 10 and 9 for a full stream.
