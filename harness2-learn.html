1. The 15-minute core 15 min

Idea 1 — Agent = Model + Harness. The model weights stay frozen. The harness is everything around the model: prompts, rules, memory, skills, tool guidance, scripts, subagents and hooks. Harness² changes only the harness.

Idea 2 — The harness is eight files. Four files are always in context (system prompt, guardrails, memory, tool guidance). Four are on demand or outside the model (skills, scripts, subagents, a plugin that hooks the tool loop). Always-on text costs tokens on every call. That is why "add another rule to the prompt" is the expensive fix.

Idea 3 — No answer key, so compare behaviour. On a new real-world task, nobody has the correct answer. Harness² runs the task once with the current harness (the reference), proposes two edited harnesses, runs each one on the same task (the probes), and then composes a final harness from the edits that changed behaviour in a way the trajectories show. This is the contrastive Propose–Probe–Compose step.

Idea 4 — Two editors with different jobs. The invariant (INV) editor fixes how the agent works: tool use, procedure, verification. The domain (DOM) editor adds what a practitioner knows: the deliverable's anatomy, decision rules, checks. Removing this split costs 2.9 points on WorkBuddy-Bench and 3.7 on JobBench (Table 3).

Idea 5 — Two levels of recursion. That is the "²". Level 1 (task-level) improves the harness for the task in front of it. Level 2 (harnessing-level) improves the improver: after each task, a reflector writes the adopted harness and a lesson (EXPERIENCE.md) into a library. The next task starts again from the clean base harness H₀, but its editors can read and copy from the library.

Idea 6 — The headline numbers. One step (k = 1) improves every model–harness configuration on all three benchmarks: up to +11.5 points on WorkBuddy-Bench (GLM-5 under OpenCode, 64.2 → 75.7, Table 1), +4.5 on JobBench, +11.8 percentage points on LAB Partial (Table 2). Parallel recursion at k = 5 adds 2.9 to 3.9 more points on WorkBuddy-Bench. With one step, GLM-5 (75.7) passes the base Gemini 3.5 Flash (72.4) on WorkBuddy-Bench.

Idea 7 — The cost and the risk. One step at k = 1 needs 4 executor runs of the same task; k = 5 needs 20 (derived in §6). The evidence is the model judging its own runs, so shared model biases can pass through: in one failure, the editor's own checker script reported PASS three times while the real tests failed (Fig. 14).

2. The problem

The same model performs differently under different harnesses. The paper's own comparison (Fig. 13, Gemini 3.5 Flash on WorkBuddy-Bench) shows that no fixed production harness wins everywhere. Claude Code is best on Code and Office. Codex is best on Web. So a harness tuned to the task matters, and hand-tuning a harness for each new kind of work costs engineering time.

Earlier automatic methods (for example Meta-Harness) search for a good harness offline, against a training set with scores, and then deploy that fixed harness. That fails in the "open world", where tasks arrive one at a time and are new. The paper names two connected problems:

  1. No ground-truth verifier at test time. A new task has no answer key, no hidden tests and no rubric. So you cannot score a harness edit before you use it.
  2. Task-specific edits do not transfer. If you carry task 1's tuned harness into task 2, the rules that were specific to task 1 become noise. But the process of fixing task 1 (how the weakness was found, which edit was tried, what the run showed) can transfer.

The central question of the paper: can recursive self-improvement improve both the current harness and how future harnesses are improved?

Why "just add rules to the prompt" is a bad fix. The editor prompt (Appendix H, Prompt 1) states the reason: always-on prose is in context on every run and competes with the agent's output budget. The paper calls the costliest failure "a run that reasons until the budget is gone and produces nothing". Adding always-on prose makes that failure more likely.

The four equations, in words:

  • Eq. 1 (H′, e′, ξ) = Φ(q_t, 𝓗, 𝓔; 𝓡_t). One step takes the task, the current harness and the history, and returns a new harness, its run and a record. The improver 𝓡_t is read-only here.

The cost order the editor must follow

Prompt 1 (Appendix H) gives the editor a strict preference order for where to put a fix. This order is the most reusable practical rule in the paper:

  1. Skill — for anything with a recognisable trigger. The default form for new instruction.
  2. Script — for a deterministic operation that the runs did by hand and got wrong, or did slowly.
  3. Subagent — for a bounded investigation whose input is large and whose answer is small. A bad trade when the output is as big as the input.
  4. Plugin — for a recurring mechanical problem in the tool loop: trim oversized tool output, append a hint after a repeated error signature, cap a runaway tool, verify a write right after it happens. Only "repeated evidence that clear prose is skipped" justifies a defensive hook, and it must not block valid completion.
  5. Always-on text last — only a short rule that applies to every run. "If you add always-on text, cut something else to pay for it."

Which components carry the gains? Table 6 removes groups from the finished k = 5 harness (Gemini 3.5 Flash, OpenCode, WorkBuddy-Bench, average 80.8). Without skills: 75.5 (−5.3). Without scripts: 77.1 (−3.7). Without the prompt group: 79.3 (−1.5). Skills matter most on Code and Web (−3.6, −6.9); scripts matter most on Office (−7.4). Every ablated harness still beats the base (72.4). Skills and scripts take about half of all edits on each benchmark (Fig. 10).

5. Task-level recursion: one contrastive step

The running example is the JobBench "producers" task in Fig. 9: reconcile schedule, roster and budget files into connected production deliverables. Executor: Gemini 3.5 Flash under OpenCode. Editor: Claude Opus 4.8 (the default editor for all runs, Appendix D.2).

Step 1 — Propose

The pipeline runs the current harness once to get the reference e₀. The reference shows how the harness behaves. It does not show whether the deliverable is correct. In the example the base run scored 43.1, and the trajectory showed two procedural failures, not knowledge gaps: (1) figures were never reconciled across files, and (2) outputs were never reopened after writing.

Two editor sessions then read the task, the harness, the reference trajectory and the library. Each writes one candidate harness by editing files on disk:

  • The INV candidate added a guardrail (C2, 1,464 B): inventory all input files with scripts/inspect_inputs.py, reconcile each figure to its source, and reopen each output with scripts/verify_outputs.py before finishing. "Confirming a file exists is not confirming it is correct." It also added the scripts (C7, 3,881 B). One script check flags a spreadsheet formula cell that a reader sees as blank.
  • The DOM candidate added a reconciliation skill (C6, 4,942 B): the source hierarchy when files disagree, committed versus conditional spend, hour caps and rest rules, completeness checks. It also added tool guidance (C4, 645 B): strip "$" and "," from numbers stored as strings; retry a timed-out web search once only; do not search the web for facts already in the workspace.

The editors have hard limits (Prompt 1). Each edit must trace to a named moment in a trajectory. The preferred evidence is a divergence (runs disagreed, so the agent can already do it), then a repeated failure, then a visible risk. "KEEP_BASE" is a valid answer. Workspace facts that the runs verified are written into the harness as facts, labelled "in this workspace…".

Step 2 — Probe

Each candidate runs on the same task with the same model and environment. The pipeline compares each probe with the reference. The comparison shows one of three things: the edit fixed the targeted behaviour, left it the same, or caused a regression. The paper is explicit that this contrast informs composition and does not verify correctness, because runs are random and the candidates share the model's biases.

Step 3 — Compose

A composer session reads the reference, both candidates, their diffs and all run evidence. It may merge supported edits, revise conflicting edits, adopt one candidate whole, or keep the current harness. Each decision must cite a concrete observation, in the form kept|revised|dropped -> <edit> -> <trajectory moment> (Prompt 3). The composed harness then runs, and that run is the delivered result.

In the example, the composer kept all four edits from the two interventions. The re-run cross-referenced the figures and restored the memo's missing sections. Score: 43.1 → 77.8 (+34.7, Fig. 9).

6. Parallel and sequential recursion

The budget k scales the step in two ways (Fig. 4, paper §2.2.2):

  • Parallel. Run k reference executions. Propose and probe k INV and k DOM candidates (2k probes). Then run k independent composers; each sees the whole pool and writes one successor, which is executed. This is one population update: k sets its width, not its depth. The idea follows Recursive Self-Aggregation (RSA), applied to executable harnesses instead of reasoning text.
  • Sequential. Chain k contrastive steps. Each step starts from the previous harness and all earlier evidence. A later step may restore a candidate that an earlier step rejected, or reproduce an earlier checkpoint.

Final selection (k > 1). An agentic selector compares anonymised deliverables against the request and the source files, and returns one existing output. It does not see which harness made which output. Picking an output from the unmodified harness is valid (Prompt 5). Its decision order: delivery, conformance (exact shape), fidelity to source, internal consistency, operational fitness, finish.

7. Harnessing-level recursion: improving the improver

After the deliverable is returned, the second level runs.

  1. Reflect. An Experience Reflector (Prompt 6) reads the full record 𝓓_t. It diffs every candidate against the base and writes one row per changed component: component, candidates, change, observed difference, verdict. Verdicts are helped, hurt, no observed effect and confounded. The prompt says to prefer confounded when one candidate changed several components at once, or when one run is all the evidence: "an invented attribution poisons the library for every later task."
  2. Write at most one lesson. A lesson has a cue (the shape of situation), a lesson (the operation on a named component), evidence and confidence. If no concrete, reusable contrast exists, the reflector writes NO_ENTRY. Adoption alone never establishes that an edit helped or will transfer (Prompt 6).
  3. Update the library. Each entry is the full adopted file tree plus its EXPERIENCE.md. An index lists all entries. Executable components stay as files, not as prose summaries. Each benchmark domain has its own library, and it starts empty (Appendix D.2). The released code adds an entry only when the reflector wrote a lesson with a cue, a lesson and evidence. After NO_ENTRY it stores nothing, not even the adopted tree (harness2/core/library.py:120, schedule.py:555).
  4. Reuse. The next task starts from H₀ again. The editors may copy a component from context/library/ into the harness, but they must re-check its workspace facts: "an earlier task's mapping or threshold is a hypothesis here, not a fact."

Does the library help? Without the library, scores fall 3.1 points on WorkBuddy-Bench and 1.8 on JobBench (Table 3). Adaptation is more common than copying: only 2–10% of modified files keep at least half their lines from a library entry (Fig. 10). A library from JobBench improves WorkBuddy-Bench one-step refinement by +0.6, +0.5 and +2.9 points on Code, Web and Office (Fig. 7 right).

Editing without running is harmful. Fig. 7 (left) edits the base harness directly, with no reference runs, no probes and no library. Code falls 73.4 → 63.2 and Web falls 69.9 → 65.0; Office rises 74.0 → 77.1. With a library built at k = 1, direct editing roughly matches the base (73.8, 72.6, 77.5). With a library built at k = 5, it gains +0.9, +4.4 and +5.1 over the base, with no probing. So more exploration on earlier tasks makes later edits better.

10. Failures and limits

Fig. 14 lists nine regressions in three groups. These are the cases to remember, because they show where label-free self-improvement breaks.

Group 1 — Blind selection picked a weaker candidate. WB-code: the pool scored 95, 85, 85, 80 and 55; the selector took the 55 as "the complete, plainest implementation" (96 → 55; the figure prints the reference as 96 and the best candidate as 95). WB-web: four of five candidates scored 100; the pick failed one static check (100 → 70). LAB transfer pricing: the selector ranked precision, but the criteria reward coverage (54 → 26).

Group 2 — The edit itself capped the pool. WB-code header injection: an edit said "keep key = name storage; it must not be 'fixed'", but the reference lowercases keys; all four candidates inherited the rule and scored 42 (50 → 42). Run one Propose–Probe–Compose step by hand

Use a task you do often, with a deliverable you can inspect. Budget: 4 runs of the task.

  1. Copy your current harness (the files in the table above) to a folder named H0/.
  2. Run the task once in a fresh session. Save the full transcript and the deliverable as the reference.
  3. Read the transcript. Write down each moment where the agent went wrong. Name the moment; a feeling is not evidence.
  4. Make candidate INV: edit only procedure, tool use and verification. Put the fix in the cheapest form: skill, then script, then subagent, then hook, then always-on text.
  5. Make candidate DOM in a separate copy: add only practitioner knowledge, as a skill with a trigger line.
  6. Run each candidate once on the same task, in a fresh session.
  7. Compare each run with the reference at the moments from step 3. Mark each edit: fixed, no change, or regression.
  8. Compose: keep only the edits with a named supporting moment. Keeping H₀ is a valid result.
  9. Run the composed harness once. This is the delivered output.
  10. Write one EXPERIENCE.md entry with cue, lesson, evidence, confidence. Write NO_ENTRY if no edit has clean evidence.

Warning — the three rules that discard a proposal (Prompt 1).

  1. Every skill needs a trigger line: its folder name must appear in always-on text ("When <situation>, load the <name> skill"). The paper calls this "the most violated rule here by a wide margin".
  2. No template braces in always-on text. Their files go through Jinja with StrictUndefined, so a doubled brace kills the job before it starts.
  3. Every script you name must exist and ship in the same proposal, at skills/<skill-name>/scripts/<file>.py for a skill's own helper.

Five rules to take away (they cost nothing to adopt).

  1. Keep always-on text short. If you add a line, delete a line.
  2. Put domain playbooks in skills with explicit trigger lines.
  3. Replace repeated hand reasoning (cell checks, format conversions) with a script.
  4. Enforce the rule that the model keeps skipping with a hook, not with more prose.
  5. Use a checker that the editing model did not write, when you can. A self-written checker shares the writer's assumptions (Fig. 14).

14. Self-test

Answer each question aloud before you open it. Return to the cited section for each miss.

1. What does the "²" in Harness² mean?

Two levels of recursion. Task-level recursion refines the execution harness for the current task. Harnessing-level recursion updates the improvement harness (its library) so that future refinement is better. §1, §7.

2. Name the eight components. Which four are always on?

C1 system prompt, C2 guardrails, C3 memory, C4 tool guidance (always on); C5 subagents, C6 skills, C7 scripts, C8 plugin. Table 5, §4.

3. Which component is the only one that adds an inference context?

C5 subagents. Each runs in its own context window and returns only its result. Table 5.

4. Why does the reference run not tell you whether the output is correct?

There is no answer key at test time. The reference shows how the harness behaves (its trajectory), which is evidence about procedure, not correctness. Paper §2.2.1, §5.

5. What does the INV editor own, and what is it forbidden to add?

It owns procedure, tool use and completion. It must not add professional rules, required domain sections or matter facts; the DOM candidate owns those. Prompt 1.

6. How many executor runs does one task cost at k = 1? At k = 5 parallel?

k = 1: 1 reference + 2 probes + 1 composed = 4. k = 5: 5 + 10 + 5 = 20. §6.

7. Rank the editor's preferred forms for a new fix.

Skill, script, subagent, plugin, always-on text last. Prompt 1, §4.

8. Which ablation costs the most on JobBench, and by how much?

Removing scoping (two generic editors instead of INV and DOM): −3.7 (36.0 → 32.3). Table 3.

9. Does the next task inherit the previous task's adopted harness?

No. Every task starts from H₀. Earlier components are reused only if an editor copies them from the library through Propose, and their workspace facts must be re-checked. Paper §2.3.

10. Why does the reflector prefer the verdict "confounded"?

When a candidate changed several components at once, or one run is the only evidence, no run isolates the cause. A wrong attribution "poisons the library for every later task". Prompt 6.

11. Is "a weaker model with a better harness beats a stronger model" true on all three benchmarks?

No. True on WorkBuddy-Bench (GLM-5 75.7 vs Gemini base 72.4). False on LAB (71.4 vs 79.9) and JobBench (24.2 vs 31.5). Tables 1 and 2, §8.

12. The video says blind editing drops performance by 10%. What is the precise claim?

Direct editing without execution, probes or library: Code 73.4 → 63.2 (−10.2 points), Web 69.9 → 65.0 (−4.9), Office 74.0 → 77.1 (+3.1). Fig. 7.

13. Name the three groups of failures in Fig. 14 and one example of each.

Blind selection took a weaker candidate (picked 55 over 95). The edit capped the pool (self-written checker PASS three times; 75 → 64). Neither edit nor pick (judge crash, 44 → 10). §10.

14. What does the Fig. 19 watchdog plugin do, exactly?

After 25 tool calls with no output file, it appends a warning to the tool result: stop researching, write every artifact. It never blocks; it only appends. §9.

15. Do the gains require a stronger editor model?

No. With the same model as executor and editor (OpenCode, k = 2), all five models improve on every benchmark; GLM-5 gains +13.7 on LAB. Fig. 8.

16. Where in Claude Code would you put a rule that the model keeps ignoring?

In a hook (C8 equivalent), for example PostToolUse or Stop, after repeated evidence that clear prose is skipped. The hook must not block valid completion. §13.

T1. The formal model

Harness² chooses files for a fixed model to read, then judges the choice without a score. To reason about it, we need four objects: the space of harnesses, a random execution, a hidden utility, and the step operator Φ.

Definition T1.1 (harness space). Model

Let \(\Sigma\) be the finite alphabet of bytes. A harness is a tuple \(H = (c_1,\dots,c_8) \in \mathcal{H} = (\Sigma^*)^8\), where \(c_i\) is the content of component \(C_i\) of the paper's Table 5 (a folder is flattened into one string). An edit is a map \(\delta : \mathcal{H} \to \mathcal{H}\) that changes a finite set of components, written \(\operatorname{supp}(\delta) \subseteq \{1,\dots,8\}\).

\(\mathcal{H}\) is countably infinite. Because every component is a file, every edit is a diff, which is the property the paper uses to make edits inspectable (paper §2.1). The editor never searches \(\mathcal{H}\) by enumeration. It proposes a few edits that a trajectory motivates.

Definition T1.2 (execution). Model of Paper §2.2.1

Fix the executor model \(\mathcal{M}\) and the environment. For a task \(q\) and a harness \(H\), an execution \(e = (\tau, y)\) is a random variable with law \(P_{q,H}\). The trajectory \(\tau\) is a finite sequence of events (model turns, tool calls, tool results), and \(y\) is the deliverable. Each run has at most 200 model turns and 3,600 seconds (Appendix D.1).

The agent is a stochastic program: the same \(q\) and \(H\) give different trajectories, because the model samples its tokens. This fact matters in T3, where one run per arm gives no estimate of the noise.

Definition T1.3 (hidden utility). Model

The benchmark grader is a function \(U_q : \mathcal{Y} \to [0,100]\). The value of a harness on task \(q\) is \[ J_q(H) = \mathbb{E}_{e \sim P_{q,H}}\big[\,U_q(y)\,\big]. \] Test-time harnessing is the problem: given \(q\) and the ability to sample from \(P_{q,\cdot}\), output a deliverable with high \(U_q\). No step of the pipeline receives \(U_q\) as an input.

This is the formal content of the paper's phrase "no ground-truth verifier". It is a harder problem than zeroth-order optimisation. A zeroth-order method observes noisy values of the objective. Here the pipeline observes no value of \(J_q\) at all. It observes only executions, and the executions do not depend on \(U_q\).

Definition T1.4 (the contrastive step Φ as a Markov kernel). Model of Paper Eq. 1

Let \(L\) be the library and \(\mathcal{E}\) the task-local history. One step \((H', e', \xi) = \Phi(q, H, \mathcal{E}; \mathcal{R}_t)\) is the composition of three random maps:

  1. Propose. Draw a reference \(e_0 \sim P_{q,H}\). Draw \(H_{\mathrm{I}} \sim \pi_{\mathrm{INV}}(\cdot \mid q, H, e_0, L)\) and \(H_{\mathrm{D}} \sim \pi_{\mathrm{DOM}}(\cdot \mid q, H, e_0, L)\).
  2. Probe. Draw \(e_{\mathrm{I}} \sim P_{q,H_{\mathrm{I}}}\) and \(e_{\mathrm{D}} \sim P_{q,H_{\mathrm{D}}}\).
  3. Compose. Draw \(H' \sim \kappa(\cdot \mid q, H, H_{\mathrm{I}}, H_{\mathrm{D}}, e_0, e_{\mathrm{I}}, e_{\mathrm{D}})\), then \(e' \sim P_{q,H'}\).

The step record \(\xi\) collects every object drawn. The editor policies \(\pi_{\mathrm{INV}}, \pi_{\mathrm{DOM}}\) and the composer \(\kappa\) are LLM sessions (Claude Opus 4.8 in the paper), so each one is a probability distribution, not a function.

The point of writing Φ this way is to see its inputs. Every kernel reads only observable data: the task, files, trajectories and the library. None reads \(U_q\). T3 proves that this restriction alone forbids any worst-case guarantee.

Composition is a search over subsets

Proposition T1.5 (composition contains selection). Model

Let \(E = E_{\mathrm{I}} \cup E_{\mathrm{D}}\) be the set of edits in the two candidates. Assume that any subset \(S \subseteq E\) applies to \(H\) without conflict, and write \(H_S\) for the result. Let \(\mathcal{C} = \{H_S : S \subseteq E\}\), and let \(\mathcal{C}_{\mathrm{sel}} = \{H, H_{E_{\mathrm{I}}}, H_{E_{\mathrm{D}}}\}\) be the outputs of the "w/o composition" ablation, which returns one whole candidate or keeps the current harness. Then \(\mathcal{C}_{\mathrm{sel}} \subseteq \mathcal{C}\), \(|\mathcal{C}| \le 2^{|E|}\), and \[ \max_{G \in \mathcal{C}} J_q(G) \;\ge\; \max_{G \in \mathcal{C}_{\mathrm{sel}}} J_q(G). \]

Proof. \(H = H_{\emptyset}\), \(H_{E_{\mathrm{I}}}\) and \(H_{E_{\mathrm{D}}}\) are the cases \(S = \emptyset\), \(S = E_{\mathrm{I}}\) and \(S = E_{\mathrm{D}}\). So every element of \(\mathcal{C}_{\mathrm{sel}}\) is in \(\mathcal{C}\). There are \(2^{|E|}\) subsets, and two subsets can give the same harness, so \(|\mathcal{C}| \le 2^{|E|}\). A maximum over a set is at least the maximum over any subset of it. ∎

The inequality is an oracle bound: it compares the best harness each method can reach, not the harness each method picks. The real composer picks with noisy behavioural evidence, so a larger space also gives more ways to pick wrong. Whether the larger space helps on average is an empirical question. The paper answers it: removing composition costs 1.6 points on WorkBuddy-Bench and 1.9 on JobBench (Table 3). In the Fig. 9 example, \(|E| = 4\), so the composer chose among at most \(2^4 = 16\) subsets, and it chose \(S = E\) (all four edits).

Parallel and sequential recursion

Definition T1.6 (width and depth). Model of Paper Eq. 2, Eq. 3

Parallel with budget \(k\): draw \(k\) references, propose \(k\) INV and \(k\) DOM candidates, probe all \(2k\), then run \(k\) composers. Each composer maps the whole pool \((\mathcal{B}, \mathcal{P})\) to one successor. This is one generation of a population method: width \(k\), depth 1 (paper §2.2.2: "\(k\) controls its width rather than its depth").

Sequential with budget \(k\): \(H^{(r)} \sim \Phi(q, H^{(r-1)}, \mathcal{E}^{(r-1)})\) for \(r = 1,\dots,k\), with \(H^{(0)} = H_0\). This is an iterated random map. Because the history \(\mathcal{E}^{(r)}\) grows at each step, the chain on harnesses alone is not time-homogeneous; the chain on (harness, history) pairs is.

Proposition T1.7 (run budget). Code harness2/core/ledger.py

In both modes, one task uses \(R(k) = 4k\) executor runs and \(P(k) = 3k\) counted improver sessions. A stream of \(N\) tasks uses \(4kN\) executor runs.

Proof. Parallel: \(k\) base runs, \(2k\) probe runs, \(k\) final runs, so \(4k\). Sequential (run_sequential in harness2/core/recursion.py): \(k\) shared base runs, then in each of \(k\) rounds two probe runs and one checkpoint run, so \(k + 3k = 4k\). Each unit of budget has one INV session, one DOM session and one composer session, so \(3k\). The selector and the reflector are recorded outside this ledger. Summing over \(N\) tasks gives \(4kN\). ∎

The cost is linear in \(k\). The return is not: on WB-code, parallel recursion goes from 76.5 at \(k = 1\) to 80.8 at \(k = 5\) (Fig. 5), so 5 times the runs bought 4.3 points there.

Proposition T1.8 (the blind selector is label-invariant). Model of Prompt 5

Let the selector see \((q, W, y_{\pi(1)}, \dots, y_{\pi(m)})\), where \(W\) is the workspace and \(\pi\) is a uniformly random permutation that hides which harness made which output. Then the probability that the selector returns the output of harness \(h\) is a function of the outputs \((y_1,\dots,y_m)\) only. It does not depend on the identity of \(h\) (for example "base" or "composed").

Proof. The selector's input contains no harness label. Fix the outputs. Swap the labels of any two harnesses whose outputs are equal: the input distribution does not change, so the probability of picking each of them does not change. More generally, the pick is a random function of the shown list, and the list depends on the harnesses only through their outputs. ∎

The selector therefore cannot favour "the harness the pipeline built" except through what that harness produced. Prompt 5 also says that returning an output of the unmodified harness is valid, so the base output stays among the options. This does not make the selector correct. The paper's Fig. 14 shows one case where it picked a 55-point output over a 95-point one.

T2. The "²": two recursions as a fold

The paper's definition couples two updates: task-level recursion refines the execution harness, and harnessing-level recursion updates the improvement harness that guides the refinement (paper §2, "Definition: Recursive Agent Harnessing"). Functional programming gives an exact shape for this coupling: a fold.

Definition T2.1 (improver state, Solve, Update). Model of Paper §2, Eq. 4

Write the improvement harness as \(\mathcal{R}_t = (\Pi, \mathcal{M}_{\mathrm{ed}}, L_t)\): the editor, composer, selector and reflector prompts \(\Pi\), the editor model \(\mathcal{M}_{\mathrm{ed}}\), and the library \(L_t\). Define

  • \(\mathrm{Solve}_{\mathcal{R}}(q, H_0)\): task-level recursion with budget \(k\), plus selection when \(k > 1\). It returns the adopted harness \(H^\star\), the deliverable \(y\), and the record \(\mathcal{D}\).
  • \(\mathrm{Update}(\mathcal{R}, H^\star, \mathcal{D})\): the reflector writes \(H^\star\) and an EXPERIENCE.md into the library (Eq. 4).

The paper says that \(\mathcal{R}_t\) "remains fixed during task-level recursion and is updated afterward through its harness improvement library" (paper §2). So in the implementation the paper describes, \(\Pi\) and \(\mathcal{M}_{\mathrm{ed}}\) stay the same and only \(L\) changes: \(L_{t+1} = L_t \cup \{(H^\star_t, X_t)\}\), where \(X_t\) is the experience file (edit rows plus one lesson or NO_ENTRY). Code The released code takes this union only when \(X_t\) holds a lesson. After NO_ENTRY, \(L_{t+1} = L_t\) (harness2/core/library.py:120).

With these definitions, a domain's whole stream of \(N\) tasks is one left fold:

\[ \mathcal{R}_{N+1} \;=\; \mathrm{foldl}\Big(\lambda\,\mathcal{R}\;q.\;\; \mathrm{Update}\big(\mathcal{R},\, \mathrm{Solve}_{\mathcal{R}}(q, H_0)\big),\;\; \mathcal{R}_1,\;\; [q_1,\dots,q_N]\Big) \]

Here \(\mathcal{R}_1\) has an empty library, because each domain's library starts empty (Appendix D.2). The fold also makes the "²" precise. The inner recursion (Φ, iterated or widened) acts on harnesses. The outer recursion acts on \(\mathcal{R}\), the object that parameterises the inner one. So the outer level is higher-order: \(\mathrm{Solve}\) has type \(\mathcal{R} \to (\text{Task} \times \mathcal{H} \to \mathcal{H} \times \mathcal{Y} \times \text{Record})\), and \(\mathrm{Update}\) maps \(\mathcal{R}\) to \(\mathcal{R}\).

Proposition T2.2 (the harness restarts; only the improver is threaded). Model

In Harness², \(H^\star_t\) is conditionally independent of \(H^\star_{1},\dots,H^\star_{t-1}\) given \((q_t, \mathcal{R}_t)\). In a carry-over design \(H_t \sim \mathrm{Solve}(q_t, H^\star_{t-1})\), this independence fails in general.

Proof. In the fold, the harness argument of \(\mathrm{Solve}\) is the constant \(H_0\) for every task. The only arguments that change between tasks are \(q_t\) and \(\mathcal{R}_t\). The earlier harnesses reach task \(t\) only as library entries, which are part of \(\mathcal{R}_t\). So, given \((q_t, \mathcal{R}_t)\), the distribution of \(H^\star_t\) is fixed. In the carry-over design, \(H^\star_{t-1}\) is a direct argument, so a change in it changes the distribution of \(H_t\) even with \(q_t\) and \(\mathcal{R}_t\) fixed. ∎

This is the formal answer to the paper's second problem (task-specific edits do not transfer). In a carry-over design, task 1's edits stay in the harness unless a later editor deletes them, and the always-on part can grow from task to task. In Harness², an earlier edit enters a later harness only if an editor copies it from the library. Prompt 1 then makes the copied facts conditional: "an earlier task's mapping or threshold is a hypothesis here, not a fact." In Bayesian terms, the library acts as a prior that the evidence of the current task can overrule, not as state that the current task inherits.

How much "self" is in this self-improvement? Model The paper places Harness² next to systems that edit model weights, improvement programs (STOP) or agent code (Darwin Gödel Machine) (paper §2). A Gödel machine (Schmidhuber, 2003) may rewrite its own source code once it proves the rewrite useful. In Harness² as described, Update does not edit \(\Pi\) or \(\mathcal{M}_{\mathrm{ed}}\). In computability terms, \(\mathcal{R}_t\) is one fixed program applied to a growing input \(L_t\). It is a learner whose memory shapes its later improvements. It is not a program that rewrites its own improvement code. The paper lists library management (merging overlapping components, revising outdated experience) as future work (Appendix G), so the library only grows: after task \(t\) it holds at most \(t\) entries, one for each task whose reflector wrote a lesson.

T3. Verification limits: what a pipeline without a grader can know

Rice's theorem, and why it is not the real obstacle

Theorem (Rice, 1953). Literature

Every non-trivial semantic property of partial computable functions is undecidable.

A harness with its model defines a program. "The deliverable is correct for every task of this kind" is a semantic, non-trivial property of that program, so no algorithm decides it in general. But Harness² does not need that general property. It runs one task, with at most 200 turns and 3,600 seconds per run, and a finite object like that can, in principle, be inspected completely. So Rice's theorem is not what stops the pipeline. What stops it is that the correctness criterion \(U_q\) is not an input to any step. The next proposition states this with no computability theory at all.

Proposition T3.1 (indistinguishability). Model

Let \(O\) be everything the pipeline observes: \(q\), the workspace, the library and all executions. Let \(f\) be any rule, deterministic or random, that maps \(O\) to a choice between harnesses \(H_a\) and \(H_b\). Suppose two graders \(U\) and \(U'\) are both possible, with \(J^{U}_q(H_a) > J^{U}_q(H_b)\) and \(J^{U'}_q(H_a) < J^{U'}_q(H_b)\). Then \(\Pr[f \text{ picks the worse harness}] \ge \tfrac12\) under \(U\) or under \(U'\).

Proof. The executions are drawn from \(P_{q,H}\), which does not depend on the grader. So \(O\) has the same distribution under \(U\) and under \(U'\), and so does the output of \(f\). Let \(p = \Pr[f \text{ picks } H_a]\). Under \(U\), the wrong pick is \(H_b\), with probability \(1-p\). Under \(U'\), the wrong pick is \(H_a\), with probability \(p\). One of \(p\) and \(1-p\) is at least \(\tfrac12\). ∎

So a guarantee needs an assumption that links what the pipeline sees to what the grader rewards. Harness² makes one, implicitly: a behavioural difference that an editor can name (figures reconciled, outputs reopened, fewer tool errors) tends to come with a higher grader score. Call it the behavioural-proxy assumption. The paper states the limit itself: behavioural contrasts "do not guarantee correctness or establish that an adopted change will transfer to a different task" (Appendix F). The mean gains in Tables 1 and 2 are evidence that the proxy holds on average on these benchmarks. They are not a per-task guarantee.

A checker written by the same model

Let \(W\) be the event "the output is wrong" and \(A\) the event "the checker script accepts". By Bayes' rule, \[ \Pr[W \mid A] = \frac{\Pr[A \mid W]\,\Pr[W]}{\Pr[A \mid W]\,\Pr[W] + \Pr[A \mid \neg W]\,\Pr[\neg W]}. \] A PASS carries information only if \(\Pr[A \mid W] \lt \Pr[A \mid \neg W]\). Illustrative numbers: let \(\Pr[W] = 0.3\) and \(\Pr[A \mid \neg W] = 0.95\). An independent checker with \(\Pr[A \mid W] = 0.1\) gives \(\Pr[W \mid A] = 0.03/0.695 \approx 0.043\). A checker that shares the executor's misreading, with \(\Pr[A \mid W] = 0.9\), gives \(\Pr[W \mid A] = 0.27/0.935 \approx 0.289\), almost the prior 0.3. The second PASS is almost worthless. The paper's Fig. 14 has the real case: a checker the editor wrote reported PASS three times while the real tests failed, and the score fell 75 → 64. The paper's comment: "A checker written by the editor cannot catch the editor's assumption."

Why "confounded" is the correct verdict

Proposition T3.2 (non-identifiability of bundled edits). Model

Model an outcome (a score or a behavioural measure) as \(Z = \beta_0 + \beta_A x_A + \beta_B x_B + \varepsilon\), where \(x_A, x_B \in \{0,1\}\) say whether components \(A\) and \(B\) changed, and \(\mathbb{E}\varepsilon = 0\). If the only observed arms are the reference \((0,0)\) and one probe \((1,1)\), then \(\beta_A\) and \(\beta_B\) are not identifiable; only \(\beta_A + \beta_B\) is.

Proof. The expected outcomes of the two arms are \(\beta_0\) and \(\beta_0 + \beta_A + \beta_B\). The parameters \((\beta_0, \beta_A, \beta_B)\) and \((\beta_0, \beta_A + c, \beta_B - c)\) give the same two expectations for every \(c\), so no data from these arms can separate them. (Equivalently, the design matrix \(\begin{pmatrix}1&0&0\\1&1&1\end{pmatrix}\) has rank 2, less than the 3 parameters.) ∎

With one run per arm, there is a second problem: the difference of two single runs has variance \(2\sigma^2\), and no estimate of \(\sigma\) is possible from one sample per arm. Prompt 6 tells the reflector to prefer confounded "whenever a candidate changed several components at once and no execution isolates one of them, or when a single rollout is all that stands behind the difference". Proposition T3.2 and the variance argument show that this is the statistically correct answer.

Being selected is not evidence of being better

Proposition T3.3 (the optimizer's curse). Literature Smith and Winkler (2006)

Let \(X_1,\dots,X_m\) be noisy estimates with \(\mathbb{E}X_j = \mu_j\), and let \(j^\star = \arg\max_j X_j\). Then \(\mathbb{E}[X_{j^\star}] \ge \mathbb{E}[\mu_{j^\star}]\): the chosen estimate overstates the chosen option's true value on average.

Proof. \[ \mathbb{E}[X_{j^\star}] = \mathbb{E}[\max_j X_j] \ge \max_j \mathbb{E}[X_j] = \max_j \mu_j \ge \mathbb{E}[\mu_{j^\star}]. \] The first inequality is Jensen's inequality, because \(\max\) is convex. The second holds because \(\mu_{j^\star}\) is one of the \(\mu_j\) for every outcome. ∎

Prompt 6 states the consequence as a rule: "Adoption alone never establishes that an edit helped or will transfer." An adoption is a maximum over noisy evidence, so the adopted harness looks better than it is. This is a different failure from a plain selector error such as Fig. 14's "picked 55 over 95", where the selector chose the worse output outright.

When the grader leaks

Proposition T3.1 assumes that \(U_q\) does not reach \(O\). The repository records a case where that failed: during a validation run with open internet access, the agent found and downloaded the benchmark's grading rubric (docs/EXPERIMENTS.md). In the model, this opens a channel from \(U_q\) into \(O\). The pipeline then optimises the grader directly, which is Goodhart's law in its plainest form, and its scores stop measuring open-world performance. The defence is to keep the channel closed: restrict network access during evaluation.

T4. The logic of enforcement: instruct versus enforce

Table 5 says the plugin C8 "enforces a behavior rather than instructs it". Temporal logic and runtime verification make this distinction exact.

Definition T4.1 (trace, safety, liveness). Literature Lamport (1977); Alpern and Schneider (1985)

A trace is a sequence of events. A property \(P\) is a set of traces. \(P\) is a safety property if every trace outside \(P\) has a finite prefix that no extension can bring back into \(P\): "nothing bad happens", and a bad event is visible at a finite point. \(P\) is a liveness property if every finite prefix can be extended to a trace in \(P\): "something good eventually happens".

Theorem (Alpern and Schneider, 1985). Literature

Every property is the intersection of a safety property and a liveness property.

Theorem (Schneider, 2000). Literature

A policy that an execution monitor can enforce, where the monitor observes the events of a run and may only halt the run, must be a safety property.

Ligatti, Bauer and Walker (2005) extended this with edit automata, which may also insert and suppress events. Edit automata can enforce more than safety properties (they enforce a class the authors call renewal properties). They also defined transparency: an enforcer is transparent if it leaves every trace that already satisfies the policy unchanged in meaning.

A prompt rule and a hook, compared

A rule written in the system prompt changes the distribution \(P_{q,H}\) over traces. It can make a violation less likely, but \(\Pr[\text{trace} \notin P]\) can stay above zero, and the paper's editor prompt names this case: "repeated evidence that clear prose is skipped" (Prompt 1). A plugin sits inside the tool loop and sees each event before the next one happens. It is a monitor in the sense above. It can block a tool call (halt-like), trim a tool result (suppress), or append a hint (insert). So a plugin is an edit automaton, and on every property it can enforce, it gives a guarantee that a prompt cannot give. The table maps the plugin uses that Prompt 1 lists to their class. The LTL operators are \(\mathbf{G}\) (always), \(\mathbf{F}\) (eventually) and \(\mathbf{X}\) (next).

Proposition T4.2 (bounded liveness is safety). Literature (standard)

For a fixed horizon \(n\), the property \[ P_n = \{\sigma : \text{a deliver event occurs at some position} \le n \text{ in } \sigma\} \] is a safety property.

Proof. Take \(\sigma \notin P_n\). Then the prefix \(\sigma[1..n]\) has no deliver event. Every extension of that prefix has the same first \(n\) events, so it also has no deliver event at a position \(\le n\), and it is not in \(P_n\). So \(\sigma[1..n]\) is a bad prefix, which is the definition of safety. ∎

This is the formal reading of the paper's costliest failure, "a run that reasons until the budget is gone and produces nothing". Without a turn cap, "eventually deliver" is liveness, and a monitor that may only halt cannot enforce it. With the cap of 200 turns, "deliver by turn 200" is a safety property: a monitor can see, at a finite point, that the run is heading for a violation, and it can insert an instruction to stop researching and write. The guarantee is partial, because the model must still produce the file after the insertion.

Prompt 1 adds a constraint on defensive hooks: a hook "must not block valid completion". This is the transparency condition: a hook that blocks "finish" with no condition breaks traces that would already deliver correctly. Read together, Prompt 1 asks for an edit automaton that is transparent, used only where prose has demonstrably failed.

T5. Learning without labels

Definition T5.1 (online harnessing with no feedback). Model

Take a finite set of \(m\) harnesses. In each round \(t = 1,\dots,N\), a task \(q_t\) arrives, the learner draws a harness \(h_t\) from a distribution \(p_t\), and suffers the loss \(\ell_t(h_t) \in [0,1]\) (for example \(1 - U_{q_t}/100\)). The learner never observes any loss. Its regret is \(\mathrm{Reg}_N = \mathbb{E}\sum_t \ell_t(h_t) - \min_h \sum_t \ell_t(h)\).

Proposition T5.2 (no feedback gives linear regret). Model

For every learner in Definition T5.1 there is a loss sequence with \(\mathrm{Reg}_N \ge N(1 - 1/m)\).

Proof. The learner observes nothing that depends on the losses. Its distributions \(p_t\) may depend on what it does observe (tasks, executions), but their averages \(\bar p_t = \mathbb{E}[p_t]\) do not depend on the losses. Fix those averages; below, \(p_t\) means \(\bar p_t\). Since \(\sum_h \sum_t p_t(h) = N\), some harness \(h^\star\) has \(\sum_t p_t(h^\star) \le N/m\). Set \(\ell_t(h^\star) = 0\) and \(\ell_t(h) = 1\) for every \(h \ne h^\star\), in every round. The learner's expected loss is \(\sum_t (1 - p_t(h^\star)) \ge N - N/m\). The best fixed harness, \(h^\star\), has loss 0. ∎

Online learning theory (Cesa-Bianchi and Lugosi, 2006) gets sublinear regret only from feedback: full loss vectors or, for bandits, the loss of the chosen action. With none, the worst case is hopeless. Harness² is in the no-feedback setting, so it cannot have a worst-case guarantee. It works because real graders are not adversaries: they reward behaviour that trajectories show, which is the behavioural-proxy assumption from T3. The positive results in Tables 1 to 3 measure how well that assumption holds on these benchmarks.

Why adapt per task at all

Proposition T5.3 (the adaptivity gap). Model

Let \(D\) be a distribution over tasks and \(\mathcal{F}\) a finite set of harnesses. Then \[ \max_{H \in \mathcal{F}} \mathbb{E}_{q \sim D}\, J_q(H) \;\le\; \mathbb{E}_{q \sim D} \max_{H \in \mathcal{F}} J_q(H), \] with equality exactly when one harness is optimal for \(D\)-almost every task.

Proof. For each \(H\) and each \(q\), \(J_q(H) \le \max_{H'} J_q(H')\). Take the expectation over \(q\), then the maximum over \(H\) on the left. For equality: let \(H^\star\) attain the left side. Then \(\mathbb{E}_q[\max_{H'} J_q(H') - J_q(H^\star)] = 0\), and the integrand is non-negative, so it is zero almost surely: \(H^\star\) is optimal for almost every task. The converse is direct. ∎

The left side is the best fixed harness. The right side is a per-task oracle. The paper's Fig. 13 shows that the gap is real for production harnesses: no fixed harness wins in every domain (Claude Code is best on Code and Office, Codex on Web). Harness² closes part of the gap. From OpenCode at \(k = 5\), it beats the best fixed harness by 4.6, 5.8 and 4.9 points on Code, Web and Office.

The library as a prior, and the cost of a false lesson

Proposition T5.4 (a false lesson costs in proportion to the remaining stream). Model

Suppose a lesson written after task \(t\) is wrong, and in each later task of the same domain it is applied with probability \(p\) and then costs \(\delta \gt 0\) points. The expected total cost over the remaining \(N - t\) tasks is \(p\,\delta\,(N - t)\).

Proof. Let \(Y_s = \delta\cdot\mathbf{1}[\text{applied in task } s]\). Then \(\mathbb{E}Y_s = p\delta\), and by linearity of expectation \(\mathbb{E}\sum_{s=t+1}^{N} Y_s = p\,\delta\,(N-t)\). No independence is needed. ∎

An early lesson has the largest reach, in both directions. This explains why Prompt 6 trades recall for precision: a lesson must rest on a concrete contrast, otherwise NO_ENTRY, because "an invented attribution poisons the library for every later task". The same linearity explains the value of a good library. Fig. 7 (left) shows that direct editing, with no probes, gains +0.9, +4.4 and +5.1 points over the base when its library was built at \(k = 5\). Exploration paid for on earlier tasks is reused on later tasks with fewer runs.

T6. A cost model for the eight components

Prompt 1 orders the places for a fix: skill, script, subagent, plugin, and always-on text last. A token-cost model explains most of this order. Let a run make \(T\) model calls, and let a component's text be \(\ell\) tokens.

  • Always-on text is in context at every call: \(\ell\,T\) context tokens per run. Prompt caching lowers the price of these tokens, but not the context they occupy. The paper's argument is about occupancy: always-on prose is "competing with the agent's own output budget" (Prompt 1).
  • A skill has a short description of \(d\) tokens that is always visible, and a body of \(\ell\) tokens loaded at call \(t_0\) when the task needs it, which happens with probability \(\pi\): \(d\,T + \pi\,\ell\,(T - t_0)\) tokens. Table 5 says a skill "costs nothing on tasks that do not need it". That is the case \(d \to 0\).

Proposition T6.1 (when a skill beats always-on text). Model

If \(\pi \lt 1 - d/\ell\), then the skill costs fewer context tokens than the same text always on.

Proof. Since \(T - t_0 \le T\), the skill costs at most \(d\,T + \pi\,\ell\,T = (d + \pi\ell)\,T\). This is less than \(\ell\,T\) exactly when \(d + \pi\ell \lt \ell\), that is, when \(\pi \lt 1 - d/\ell\). ∎

Illustrative numbers: the Fig. 9 skill is 4,942 B, about 1,200 tokens at an assumed 4 bytes per token. With a 50-token description, the skill wins unless more than about 96% of tasks need it (\(1 - 50/1200 \approx 0.958\)). That is why the skill is the default home for new instruction.

  • A subagent reads an input of \(I\) tokens in its own context and returns a result of \(r\) tokens. Reading the input in the main context would keep \(I\) tokens there for the remaining \(T_r\) calls. The subagent keeps \(r\), at an overhead \(o\) for its own calls. It saves context when \((I - r)\,T_r \gt o\). When \(r \approx I\), the left side is near zero, which is Prompt 1's rule: a subagent is "a bad trade when the output is as big as the input".
  • A script replaces many reasoned checks with one deterministic program. If a model checks \(n\) items with an independent error rate \(\varepsilon\) per item, the chance of no error is \((1-\varepsilon)^n \le e^{-\varepsilon n}\). Illustrative: \(\varepsilon = 0.01\) and \(n = 500\) give \(0.99^{500} \approx 0.0066\). A correct script has no per-item error. The risk moves into the script's own code, where a bug is systematic (it hits every item). One check of the code covers all 500 items.
  • A plugin costs few tokens, but it can block valid behaviour (T4). Its cost is a risk to correct runs, not tokens, which is why Prompt 1 requires repeated evidence before adding one.

The paper's component ablation agrees with the model's ranking of what carries value. Removing skills from the finished \(k = 5\) harness costs 5.3 points, scripts 3.7, and the always-on prompt group 1.5 (Table 6). Skills and scripts take about half of all edits on each benchmark (Fig. 10).

T8. Exercises

1. How many executor runs and counted sessions does sequential recursion use at k = 4?

\(R = 4k = 16\) runs (4 base, 8 probes, 4 checkpoints) and \(P = 3k = 12\) sessions (4 INV, 4 DOM, 4 composers), by Proposition T1.7. The selector and reflector are extra and are not in the ledger.

2. Proposition T1.5 shows that composition can reach every harness that selection can reach. Why does this not prove that composition helps?

It is an oracle bound on the best reachable harness. The composer chooses with noisy behavioural evidence and no grader, so it may choose a worse subset. Only the ablation in Table 3 shows that composition helps on average.

3. A candidate changed C2 and C7 together, and its probe behaved better than the reference. Which verdict should the reflector give for C2?

confounded. With only the arms \((0,0)\) and \((1,1)\), only the sum of the two effects is identifiable (Proposition T3.2), and one run per arm gives no noise estimate.

4. Why can a hook enforce "deliver within 200 turns" but not "deliver eventually" by blocking?

"Within 200 turns" is a safety property (Proposition T4.2): a violation is visible at a finite prefix, so a monitor can act before turn 200. "Eventually" is liveness: no finite prefix shows a violation, and halting a run can only make the property false (Schneider, 2000). Even for the bounded version, the hook can only insert an instruction; the model must still write the file.

5. With m = 2 harnesses and N = 100 tasks and no feedback, what regret can an adversary force?

At least \(N(1 - 1/m) = 50\) (Proposition T5.2).

6. A skill has a 40-token description and a 400-token body. Above which trigger probability is always-on text cheaper by the bound of Proposition T6.1?

The bound guarantees the skill is cheaper when \(\pi \lt 1 - 40/400 = 0.9\). Above 0.9 the bound says nothing, and always-on text can be cheaper; the exact answer also depends on \(t_0\).

7. Is Harness² a Gödel machine?

No, as described. A Gödel machine rewrites its own code after it proves the rewrite useful. Harness² keeps its prompts and editor model fixed and updates only the library (paper §2; Appendix G lists library management as future work). It is a fixed improver with a growing memory.
