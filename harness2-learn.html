1. The 15-minute core 15 min

Idea 1 — Agent = Model + Harness. The model weights stay frozen. The harness is everything around the model: prompts, rules, memory, skills, tool guidance, scripts, subagents and hooks. Harness² changes only the harness.

Idea 2 — The harness is eight files. Four files are always in context (system prompt, guardrails, memory, tool guidance). Four are on demand or outside the model (skills, scripts, subagents, a plugin that hooks the tool loop). Always-on text costs tokens on every call. That is why "add another rule to the prompt" is the expensive fix.

Idea 3 — No answer key, so compare behaviour. On a new real-world task, nobody has the correct answer. Harness² runs the task once with the current harness (the reference), proposes two edited harnesses, runs each one on the same task (the probes), and then composes a final harness from the edits that changed behaviour in a way the trajectories show. This is the contrastive Propose–Probe–Compose step.

Idea 4 — Two editors with different jobs. The invariant (INV) editor fixes how the agent works: tool use, procedure, verification. The domain (DOM) editor adds what a practitioner knows: the deliverable's anatomy, decision rules, checks. Removing this split costs 2.9 points on WorkBuddy-Bench and 3.7 on JobBench (Table 3).

Idea 5 — Two levels of recursion. That is the "²". Level 1 (task-level) improves the harness for the task in front of it. Level 2 (harnessing-level) improves the improver: after each task, a reflector writes the adopted harness and a lesson (EXPERIENCE.md) into a library. The next task starts again from the clean base harness H₀, but its editors can read and copy from the library.

Idea 6 — The headline numbers. One step (k = 1) improves every model–harness configuration on all three benchmarks: up to +11.5 points on WorkBuddy-Bench (GLM-5 under OpenCode, 64.2 → 75.7, Table 1), +4.5 on JobBench, +11.8 percentage points on LAB Partial (Table 2). Parallel recursion at k = 5 adds 2.9 to 3.9 more points on WorkBuddy-Bench. With one step, GLM-5 (75.7) passes the base Gemini 3.5 Flash (72.4) on WorkBuddy-Bench.

Idea 7 — The cost and the risk. One step at k = 1 needs 4 executor runs of the same task; k = 5 needs 20 (derived in §6). The evidence is the model judging its own runs, so shared model biases can pass through: in one failure, the editor's own checker script reported PASS three times while the real tests failed (Fig. 14).

2. The problem

The same model performs differently under different harnesses. The paper's own comparison (Fig. 13, Gemini 3.5 Flash on WorkBuddy-Bench) shows that no fixed production harness wins everywhere. Claude Code is best on Code and Office. Codex is best on Web. So a harness tuned to the task matters, and hand-tuning a harness for each new kind of work costs engineering time.

Earlier automatic methods (for example Meta-Harness) search for a good harness offline, against a training set with scores, and then deploy that fixed harness. That fails in the "open world", where tasks arrive one at a time and are new. The paper names two connected problems:

  1. No ground-truth verifier at test time. A new task has no answer key, no hidden tests and no rubric. So you cannot score a harness edit before you use it.
  2. Task-specific edits do not transfer. If you carry task 1's tuned harness into task 2, the rules that were specific to task 1 become noise. But the process of fixing task 1 (how the weakness was found, which edit was tried, what the run showed) can transfer.

The central question of the paper: can recursive self-improvement improve both the current harness and how future harnesses are improved?

Why "just add rules to the prompt" is a bad fix. The editor prompt (Appendix H, Prompt 1) states the reason: always-on prose is in context on every run and competes with the agent's output budget. The paper calls the costliest failure "a run that reasons until the budget is gone and produces nothing". Adding always-on prose makes that failure more likely.

The paper uses a small notation. You need it only to read Section 2 of the paper. Each symbol below has a plain meaning.

The four equations, in words:

  • Eq. 1 (H′, e′, ξ) = Φ(q_t, 𝓗, 𝓔; 𝓡_t). One step takes the task, the current harness and the history, and returns a new harness, its run and a record. The improver 𝓡_t is read-only here.
  • Eq. 2 H′_j = Compose_j(q_t, 𝓗, 𝓑, 𝓟; 𝓡_t), j = 1…k. Parallel: k composers each see all k reference runs (𝓑) and the full pool of candidates with their runs (𝓟), and each writes one successor.
  • Eq. 3 (H⁽ʳ⁾, e⁽ʳ⁾, ξ⁽ʳ⁾) = Φ(q_t, H⁽ʳ⁻¹⁾, 𝓔⁽ʳ⁻¹⁾; 𝓡_t), r = 1…k. Sequential: chain k steps; each step starts from the previous harness and all earlier evidence.
  • Eq. 4 𝓡_{t+1} = Update(𝓡_t, H★_t, 𝓓_t). After the task, the library gains the adopted harness and the supported lessons.

The harness is a file tree. The paper takes the file-level split from AHE and adds one component; the paper does not say which one (paper §2.1, Table 5). In the stock harness, the always-on files hold only the benchmark's instructions, and each on-demand folder holds a placeholder. The placeholder exists so that the editor can discover that the component exists.

The cost order the editor must follow

Prompt 1 (Appendix H) gives the editor a strict preference order for where to put a fix. This order is the most reusable practical rule in the paper:

  1. Skill — for anything with a recognisable trigger. The default form for new instruction.
  2. Script — for a deterministic operation that the runs did by hand and got wrong, or did slowly.
  3. Subagent — for a bounded investigation whose input is large and whose answer is small. A bad trade when the output is as big as the input.
  4. Plugin — for a recurring mechanical problem in the tool loop: trim oversized tool output, append a hint after a repeated error signature, cap a runaway tool, verify a write right after it happens. Only "repeated evidence that clear prose is skipped" justifies a defensive hook, and it must not block valid completion.
  5. Always-on text last — only a short rule that applies to every run. "If you add always-on text, cut something else to pay for it."

Which components carry the gains? Table 6 removes groups from the finished k = 5 harness (Gemini 3.5 Flash, OpenCode, WorkBuddy-Bench, average 80.8). Without skills: 75.5 (−5.3). Without scripts: 77.1 (−3.7). Without the prompt group: 79.3 (−1.5). Skills matter most on Code and Web (−3.6, −6.9); scripts matter most on Office (−7.4). Every ablated harness still beats the base (72.4). Skills and scripts take about half of all edits on each benchmark (Fig. 10).

5. Task-level recursion: one contrastive step

The running example is the JobBench "producers" task in Fig. 9: reconcile schedule, roster and budget files into connected production deliverables. Executor: Gemini 3.5 Flash under OpenCode. Editor: Claude Opus 4.8 (the default editor for all runs, Appendix D.2).

Step 1 — Propose

The pipeline runs the current harness once to get the reference e₀. The reference shows how the harness behaves. It does not show whether the deliverable is correct. In the example the base run scored 43.1, and the trajectory showed two procedural failures, not knowledge gaps: (1) figures were never reconciled across files, and (2) outputs were never reopened after writing.

Two editor sessions then read the task, the harness, the reference trajectory and the library. Each writes one candidate harness by editing files on disk:

  • The INV candidate added a guardrail (C2, 1,464 B): inventory all input files with scripts/inspect_inputs.py, reconcile each figure to its source, and reopen each output with scripts/verify_outputs.py before finishing. "Confirming a file exists is not confirming it is correct." It also added the scripts (C7, 3,881 B). One script check flags a spreadsheet formula cell that a reader sees as blank.
  • The DOM candidate added a reconciliation skill (C6, 4,942 B): the source hierarchy when files disagree, committed versus conditional spend, hour caps and rest rules, completeness checks. It also added tool guidance (C4, 645 B): strip "$" and "," from numbers stored as strings; retry a timed-out web search once only; do not search the web for facts already in the workspace.

The editors have hard limits (Prompt 1). Each edit must trace to a named moment in a trajectory. The preferred evidence is a divergence (runs disagreed, so the agent can already do it), then a repeated failure, then a visible risk. "KEEP_BASE" is a valid answer. Workspace facts that the runs verified are written into the harness as facts, labelled "in this workspace…".

Step 2 — Probe

Each candidate runs on the same task with the same model and environment. The pipeline compares each probe with the reference. The comparison shows one of three things: the edit fixed the targeted behaviour, left it the same, or caused a regression. The paper is explicit that this contrast informs composition and does not verify correctness, because runs are random and the candidates share the model's biases.

Step 3 — Compose

A composer session reads the reference, both candidates, their diffs and all run evidence. It may merge supported edits, revise conflicting edits, adopt one candidate whole, or keep the current harness. Each decision must cite a concrete observation, in the form kept|revised|dropped -> <edit> -> <trajectory moment> (Prompt 3). The composed harness then runs, and that run is the delivered result.

In the example, the composer kept all four edits from the two interventions. The re-run cross-referenced the figures and restored the memo's missing sections. Score: 43.1 → 77.8 (+34.7, Fig. 9).

A trap in the example. This +34.7 is one task. It is not a benchmark mean. The JobBench mean gain for the same configuration at k = 1 is +4.5 (31.5 → 36.0, Table 2). The scores are always computed after the fact by the benchmark's grader, and the pipeline never sees them.

Composition is worth 1.6 points on WorkBuddy-Bench and 1.9 on JobBench. The "w/o composition" ablation probes both candidates and returns whichever the evidence favours, without merging (Table 3).

6. Parallel and sequential recursion

The budget k scales the step in two ways (Fig. 4, paper §2.2.2):

  • Parallel. Run k reference executions. Propose and probe k INV and k DOM candidates (2k probes). Then run k independent composers; each sees the whole pool and writes one successor, which is executed. This is one population update: k sets its width, not its depth. The idea follows Recursive Self-Aggregation (RSA), applied to executable harnesses instead of reasoning text.
  • Sequential. Chain k contrastive steps. Each step starts from the previous harness and all earlier evidence. A later step may restore a candidate that an earlier step rejected, or reproduce an earlier checkpoint.

Final selection (k > 1). An agentic selector compares anonymised deliverables against the request and the source files, and returns one existing output. It does not see which harness made which output. Picking an output from the unmodified harness is valid (Prompt 5). Its decision order: delivery, conformance (exact shape), fidelity to source, internal consistency, operational fitness, finish.

Each executor run is capped at 200 model turns and 3,600 seconds (Appendix D.1). Parallel sessions can run at the same time, so latency can be lower than the run count suggests, but the compute is not lower.

What the budget buys. On WB-code, parallel recursion goes from 76.5 (k = 1) to 80.8 (k = 5). On WB-office it goes from 79.5 to 83.4 (Fig. 5). Both forms rise steadily from k = 1 to 5. Both forms at k = 2 beat every plotted baseline at k = 5. Parallel finishes above sequential at k = 5, but sequential is higher on Code at k = 2. Harness Scaling (a baseline that also spends extra test-time budget) drops from k = 2 to 3 on both domains. So more test-time exploration alone does not give better results; the recursive composition does.

7. Harnessing-level recursion: improving the improver

After the deliverable is returned, the second level runs.

  1. Reflect. An Experience Reflector (Prompt 6) reads the full record 𝓓_t. It diffs every candidate against the base and writes one row per changed component: component, candidates, change, observed difference, verdict. Verdicts are helped, hurt, no observed effect and confounded. The prompt says to prefer confounded when one candidate changed several components at once, or when one run is all the evidence: "an invented attribution poisons the library for every later task."
  2. Write at most one lesson. A lesson has a cue (the shape of situation), a lesson (the operation on a named component), evidence and confidence. If no concrete, reusable contrast exists, the reflector writes NO_ENTRY. Being selected is never evidence that an edit helped.
  3. Update the library. Each entry is the full adopted file tree plus its EXPERIENCE.md. An index lists all entries. Executable components stay as files, not as prose summaries. Each benchmark domain has its own library, and it starts empty (Appendix D.2).
  4. Reuse. The next task starts from H₀ again. The editors may copy a component from context/library/ into the harness, but they must re-check its workspace facts: "an earlier task's mapping or threshold is a hypothesis here, not a fact."

Does the library help? Without the library, scores fall 3.1 points on WorkBuddy-Bench and 1.8 on JobBench (Table 3). Adaptation is more common than copying: only 2–10% of modified files keep at least half their lines from a library entry (Fig. 10). A library from JobBench improves WorkBuddy-Bench one-step refinement by +0.6, +0.5 and +2.9 points on Code, Web and Office (Fig. 7 right).

Editing without running is harmful. Fig. 7 (left) edits the base harness directly, with no reference runs, no probes and no library. Code falls 73.4 → 63.2 and Web falls 69.9 → 65.0; Office rises 74.0 → 77.1. With a library built at k = 1, direct editing roughly matches the base (73.8, 72.6, 77.5). With a library built at k = 5, it gains +0.9, +4.4 and +5.1 over the base, with no probing. So more exploration on earlier tasks makes later edits better.

  • Against baselines. Harness² beats every baseline on WorkBuddy-Bench average and JobBench in all four configurations. On LAB, Meta-Harness leads for Gemini under Codex (76.5 against 75.6). ReasoningBank falls up to 6.6 points below base on coding (GLM-5 / Codex Code, 56.8 → 50.2). Harness Scaling is below base in 7 of 12 pairs.
  • Weaker models gain more on WorkBuddy-Bench and LAB. GLM-5 gains +11.5 and +10.9 on WorkBuddy-Bench average; Gemini gains +5.1 and +3.0. On JobBench the order reverses: Gemini +4.5 and +1.4, GLM-5 +3.6 and +1.2.
  • "Harness over model" has limits. GLM-5 with one step (75.7, 75.3) passes base Gemini (72.4, 74.5) on WorkBuddy-Bench. On LAB, GLM-5 with one step (71.4, 65.9) stays below base Gemini (79.9, 71.6). On JobBench, GLM-5 (24.2, 24.8) stays below base Gemini (31.5, 33.9).

Tool calls fall on WorkBuddy-Bench (20.0 → 17.8) but rise on JobBench (27.4 → 32.8) and LAB (20.8 → 25.2).

10. Failures and limits

Fig. 14 lists nine regressions in three groups. These are the cases to remember, because they show where label-free self-improvement breaks.

Group 1 — Blind selection picked a weaker candidate. WB-code: the pool scored 95, 85, 85, 80 and 55; the selector took the 55 as "the complete, plainest implementation" (96 → 55; the figure prints the reference as 96 and the best candidate as 95). WB-web: four of five candidates scored 100; the pick failed one static check (100 → 70). LAB transfer pricing: the selector ranked precision, but the criteria reward coverage (54 → 26).

Group 2 — The edit itself capped the pool. WB-code header injection: an edit said "keep key = name storage; it must not be 'fixed'", but the reference lowercases keys; all four candidates inherited the rule and scored 42 (50 → 42). WB-code validator cache: the edit said an id()-keyed cache is enough, and the skill's own checker reported PASS three times — "A checker written by the editor cannot catch the editor's assumption" (75 → 64). LAB notice of deficiency: a skill pre-decided a legal position that the criterion rewards the opposite of (83 → 81).

Group 3 — Neither the edit nor the pick. JobBench web administrators: a bimodal all-or-nothing criterion, sampling noise (31 → 24). WB-web particle boundary: three judge sessions returned no verdict; a judge crash, not a harness fault (44 → 10). JobBench court clerks: a PDF form-filling skill worked (33 of 33 values confirmed) but no criterion reads those PDFs; 85 of 132 steps went into it (16 → 8).

Stated limitations (Appendix F). (1) Cost: more executions and editor sessions; parallel runs cut latency, not compute; only a bounded budget range was tested. (2) Execution-based feedback is sensitive to run variability and shared model biases; it does not guarantee correctness or transfer.

Future work (Appendix G). Manage a growing library (merge overlaps, retire old lessons, better retrieval). Choose the recursion form and budget per task, and stop when more probes add little new evidence.

12. The code release

Warning — three setup facts before you start.

  1. The README says cp .env.example .env, but the repository has no .env.example. Create .env by hand. Required: HARNESS2_SOLVER_MODEL (OpenCode provider/model form). Common: GOOGLE_CLOUD_PROJECT, HARNESS2_IMPROVER_MODEL, HARNESS2_JUDGE_MODEL, HARNESS2_RUNS_DIR.
  2. Model runs cost API money. Start with --dry-run and --max-tasks 1. Model-backed runs also need Node.js 20+ and the Google Cloud CLI; WorkBuddy needs Docker; LAB needs pandoc and poppler-utils.
  3. The improver channel claude_cli runs claude --dangerously-skip-permissions -p. Run it only in a sandbox.

The rubric-download story

This story is in docs/EXPERIMENTS.md ("Web access"), not in the paper: "In a validation run of this release, a Codex rollout on JobBench downloaded its task's rubric without being instructed to." JobBench publishes each task's RUBRICS.json on Hugging Face, and the release does not restrict network access. The docs tell you to block huggingface.co, hf.co, *.hf.co, github.com and raw.githubusercontent.com for the executor at the network level (egress firewall or DNS), because Codex runs with its sandbox disabled.

Other notes from the repo: --seed sets task order only, not model sampling. A failed judge stays unscored, not zero. The repo does not show how GLM-5 was served; dependencies/PINNED.md says paper runs "may have used different tasks, model deployments, and additional local tooling".

13. Apply it to your Claude Code harness

The eight components map almost one-to-one onto the parts of Claude Code that you already build. This mapping is my reading; the paper tests OpenCode and Codex, and uses Claude Code only as a fixed comparison harness (Fig. 13).

The paper's watchdog (Fig. 19) has a direct Claude Code form: a PostToolUse hook that counts calls and adds context after N calls with no output file. The paper's "block finish until outputs verify" pattern has a Stop hook form. Follow the paper's rule for C8: add a hook only after repeated evidence that clear prose is skipped, and never block valid completion.

Run one Propose–Probe–Compose step by hand

Use a task you do often, with a deliverable you can inspect. Budget: 4 runs of the task.

  1. Copy your current harness (the files in the table above) to a folder named H0/.
  2. Run the task once in a fresh session. Save the full transcript and the deliverable as the reference.
  3. Read the transcript. Write down each moment where the agent went wrong. Name the moment; a feeling is not evidence.
  4. Make candidate INV: edit only procedure, tool use and verification. Put the fix in the cheapest form: skill, then script, then subagent, then hook, then always-on text.
  5. Make candidate DOM in a separate copy: add only practitioner knowledge, as a skill with a trigger line.
  6. Run each candidate once on the same task, in a fresh session.
  7. Compare each run with the reference at the moments from step 3. Mark each edit: fixed, no change, or regression.
  8. Compose: keep only the edits with a named supporting moment. Keeping H₀ is a valid result.
  9. Run the composed harness once. This is the delivered output.
  10. Write one EXPERIENCE.md entry with cue, lesson, evidence, confidence. Write NO_ENTRY if no edit has clean evidence.

Warning — the three rules that discard a proposal (Prompt 1).

  1. Every skill needs a trigger line: its folder name must appear in always-on text ("When <situation>, load the <name> skill"). The paper calls this "the most violated rule here by a wide margin".
  2. No template braces in always-on text. Their files go through Jinja with StrictUndefined, so a doubled brace kills the job before it starts.
  3. Every script you name must exist and ship in the same proposal, at skills/<skill-name>/scripts/<file>.py for a skill's own helper.

Five rules to take away (they cost nothing to adopt).

  1. Keep always-on text short. If you add a line, delete a line.
  2. Put domain playbooks in skills with explicit trigger lines.
  3. Replace repeated hand reasoning (cell checks, format conversions) with a script.
  4. Enforce the rule that the model keeps skipping with a hook, not with more prose.
  5. Use a checker that the editing model did not write, when you can. A self-written checker shares the writer's assumptions (Fig. 14).

14. Self-test

Answer each question aloud before you open it. Return to the cited section for each miss.

1. What does the "²" in Harness² mean?

Two levels of recursion. Task-level recursion refines the execution harness for the current task. Harnessing-level recursion updates the improvement harness (its library) so that future refinement is better. §1, §7.

2. Name the eight components. Which four are always on?

C1 system prompt, C2 guardrails, C3 memory, C4 tool guidance (always on); C5 subagents, C6 skills, C7 scripts, C8 plugin. Table 5, §4.

3. Which component is the only one that adds an inference context?

C5 subagents. Each runs in its own context window and returns only its result. Table 5.

4. Why does the reference run not tell you whether the output is correct?

There is no answer key at test time. The reference shows how the harness behaves (its trajectory), which is evidence about procedure, not correctness. Paper §2.2.1, §5.

5. What does the INV editor own, and what is it forbidden to add?

It owns procedure, tool use and completion. It must not add professional rules, required domain sections or matter facts; the DOM candidate owns those. Prompt 1.

6. How many executor runs does one task cost at k = 1? At k = 5 parallel?

k = 1: 1 reference + 2 probes + 1 composed = 4. k = 5: 5 + 10 + 5 = 20. §6.

7. Rank the editor's preferred forms for a new fix.

Skill, script, subagent, plugin, always-on text last. Prompt 1, §4.

8. Which ablation costs the most on JobBench, and by how much?

Removing scoping (two generic editors instead of INV and DOM): −3.7 (36.0 → 32.3). Table 3.

9. Does the next task inherit the previous task's adopted harness?

No. Every task starts from H₀. Earlier components are reused only if an editor copies them from the library through Propose, and their workspace facts must be re-checked. Paper §2.3.

10. Why does the reflector prefer the verdict "confounded"?

When a candidate changed several components at once, or one run is the only evidence, no run isolates the cause. A wrong attribution "poisons the library for every later task". Prompt 6.

11. Is "a weaker model with a better harness beats a stronger model" true on all three benchmarks?

No. True on WorkBuddy-Bench (GLM-5 75.7 vs Gemini base 72.4). False on LAB (71.4 vs 79.9) and JobBench (24.2 vs 31.5). Tables 1 and 2, §8.

12. The video says blind editing drops performance by 10%. What is the precise claim?

Direct editing without execution, probes or library: Code 73.4 → 63.2 (−10.2 points), Web 69.9 → 65.0 (−4.9), Office 74.0 → 77.1 (+3.1). Fig. 7.

13. Name the three groups of failures in Fig. 14 and one example of each.

Blind selection took a weaker candidate (picked 55 over 95). The edit capped the pool (self-written checker PASS three times; 75 → 64). Neither edit nor pick (judge crash, 44 → 10). §10.

14. What does the Fig. 19 watchdog plugin do, exactly?

After 25 tool calls with no output file, it appends a warning to the tool result: stop researching, write every artifact. It never blocks; it only appends. §9.

15. Do the gains require a stronger editor model?

No. With the same model as executor and editor (OpenCode, k = 2), all five models improve on every benchmark; GLM-5 gains +13.7 on LAB. Fig. 8.

16. Where in Claude Code would you put a rule that the model keeps ignoring?

In a hook (C8 equivalent), for example PostToolUse or Stop, after repeated evidence that clear prose is skipped. The hook must not block valid completion. §13.
