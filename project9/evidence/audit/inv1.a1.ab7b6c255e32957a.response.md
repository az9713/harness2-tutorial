Moment that motivated it: in `context/rollouts/base1.md`, the agent follows AGENTS.md exactly — reads `ledger.csv` (rows `100.25,posted`, `-20.10,posted`, `5.00,posted`), runs `python3 scripts/summarize.py ledger.csv`, gets `Total: 105.25`, and writes that straight to `answer.txt` without question (`context/deliverables/base1/answer.txt` = "Total: 105.25"). The correct signed sum per `context/task.md` ("Sum the signed amounts. A value in parentheses is negative. Skip rows whose status is void.") is 100.25 − 20.10 + 5.00 = 85.15. The old script computed `sum(amount for amount in rows if amount > 0)` — it silently dropped every negative entry instead of summing it with its sign, and never implemented parentheses-as-negative or void-skipping at all. The one available rollout shows the agent complying with AGENTS.md's "don't compute it yourself, trust the script" instruction to the letter and landing on a wrong answer as a direct, deterministic consequence — not an agent mistake, a broken tool mistake.

Why this is the right lever for the INV dimension: the mission explicitly assigns `scripts/<name>.py` to this dimension as the home for "repeated deterministic extraction, conversion or checking, with clear inputs, outputs and failure behavior." The script's whole job (its stated contract, per both task.md and the AGENTS.md framing of it as "the house method") was to compute exactly this signed/parens/void sum — it just didn't actually do that. Fixing it doesn't add a new domain rule or professional judgment call; it makes an existing owned component meet the one specification already given, so the existing AGENTS.md instruction to delegate arithmetic to the script (good practice — keeps the LLM from hand-computing sums on potentially larger ledgers) becomes safe to keep as-is.

Also relevant: per the "ground it in this workspace" guidance, this harness is filed in the domain library and will be read as an example for other ledger-reconciliation tasks, which may actually contain parentheses or void rows (this particular `ledger.csv` sample happens to have neither). A script that only coincidentally produced a plausible-looking number on this one ledger, but implemented none of the stated parens/void rules, would silently misreconcile the next ledger that uses either convention. The fix implements both rules directly (strip `()`→negate; skip rows where `status` lowercased is `void`), scoped tightly to what task.md actually specifies — no invented extras like currency symbols or thousands separators, since nothing in the evidence calls for them.
